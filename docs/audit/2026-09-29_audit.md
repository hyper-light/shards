# Shards codebase audit — 2026-09-29

**Verdict:** Shards has a credible route to fast, compact microVM execution, and unusually useful research and integration tests. It does not yet satisfy “beat Firecracker on speed and resource utilization without sacrificing correctness.” The initial review found reproducible snapshot corruption, credential forwarding outside the intended origin, execution after successful container removal, silent output loss, and broken shutdown and pool configurations. Memory access and VM ownership also have unsafe contracts that the safe APIs do not enforce.

These are substantive defects in implemented behavior. Correctness repairs, bounded resource ownership, and a fleet benchmark should precede further headline latency work.

**Continuation:** the allocation, copying, retention, and page-fault review below examines **38457b709e67c4a43de87adfd7f2053531672dc2**. Concurrent repairs have closed A03/A05/A16/A18 and changed kernel provisioning for A19; the initial findings remain historical evidence. The continuation adds reproducible memory-serialization defects, measured RAM materialization during sparse saving, allocation censuses, and concrete optimization designs. See [the continuation](#allocation-copying-retention-and-page-fault-continuation) and the maintained [response tracker](2026-09-29_response.md).

## What the product actually does

Shards is a pre-release, rootless microVM execution platform for agent workloads. Its long-term product is a Linux machine shared by multiple isolated agents, with Docker/Compose interfaces, networking, filesystem and device policy, and GPU access. **The implemented execution model is currently one microVM per container run.** The shared Engine and per-agent isolation are planned architecture, not current functionality.

The working stack is:

1. A small `shards` CLI parses Docker-like command lines and connects to `shardsd` using local IPC and descriptor passing.
2. The daemon resolves OCI/Docker images, obtains Docker credentials and registry trust settings, fetches manifests/configuration/layers, and prepares an immutable root filesystem.
3. Compressed blobs are content-addressed; fresh ingestion checks descriptor size and digest. Decompressed layers are checked against DiffIDs, flattened with layer semantics, and written as EROFS keyed by ChainID.
4. A separate `shards-vm` process creates the VM. Today, functional backends are macOS arm64/HVF and Linux x86_64/KVM. Other advertised build targets compile but have no VM backend.
5. The Linux `shards-init` PID 1 mounts the EROFS image through read-only virtio-pmem, creates a per-VM tmpfs overlay, prepares a standby process, and waits for relevant boot work before requesting a template snapshot.
6. A template is taken **before the workload**. Its key includes guest kernel/init digests, rootfs path, CPU/RAM shape, command line, and snapshot format. Restores receive a new VM generation ID; the workload path synchronizes wall-clock time and supplies a fresh command over vsock.
7. The daemon keeps two ready restored VMs **per template** by default. Each receives one run; a replacement is restored in the background.
8. Init resolves the image/request user and environment, execs the workload, relays pipes or a terminal, forwards signals, reaps descendants, and reports status. The host records logs and lifecycle state for `ps`, `wait`, `logs`, `stop`, `kill`, and `rm`.

The guest ABI announcement now rejects an init built for another contract before sending a workload. That is a useful correctness improvement and is included in the final validation.

The critical boundaries are therefore **registry → trusted image store**, **guest RAM/virtqueues → host device code**, **CPU/device state → reusable snapshot**, and **client request → container ownership/status/output**. A fast successful run exercises only a small subset of those boundaries.

The sub-200 µs restore/resume figures and roughly 3 ms pooled command figures describe different stages. Neither is a fresh Linux boot, a multi-agent Engine start, nor a complete sustained-service capacity measurement. Sources: [README](../../README.md), [architecture](../design/architecture.md), [benchmark methods and results](../benchmarks.md).

### A01 — Shared guest-memory access has an unenforced safety contract

**Where:** [GuestMemory Send/Sync and accessors](../../crates/vmm/src/memory.rs#L63), especially lines 180–215; [snapshot memory saving](../../crates/vmm/src/memory.rs#L129).

`GuestMemory` is explicitly Send + Sync, but `read`, `write`, `read_obj`, and `write_obj` accept shared references and use ordinary non-atomic raw reads/writes. Two entirely safe Rust callers can share an Arc and concurrently write/read the same GPA. The type also exposes an atomic u16 view while retaining safe non-atomic access to those same bytes. Bounds checks do not establish synchronization.

This matters in production: block and vsock workers share guest RAM, and a guest controls descriptor addresses, including overlap between queues/devices. Separately, `save(&self)` creates an ordinary shared byte slice while its “all CPUs/devices paused” precondition exists only in prose. A safe caller can violate that precondition.

**Required change:** establish an explicit memory-access model. Use audited guest-memory/volatile abstractions for externally modified memory, enforce host-versus-host synchronization and atomic access rules, and require an exclusive stopped-machine capability for ordinary bulk slices and snapshot copying. **Volatile access alone does not synchronize competing Rust threads.** Merely deleting the safety comment, adding fences around a memcpy, or replacing every load with volatile does not close the safe-API hole.

**Validation:** demonstrate that safe callers cannot race overlapping host accesses; test descriptor aliasing across devices and atomic-index overlap; use a sanitizer-supported host harness and a model/tool capable of checking the abstraction. Keep all current ring ordering tests. Rust defines data races as undefined behavior; rust-vmm's volatile-memory documentation is useful background, not proof that a mechanical substitution is sufficient. [Rust undefined behavior rules](https://doc.rust-lang.org/reference/behavior-considered-undefined.html), [rust-vmm volatile memory](https://docs.rs/vm-memory/latest/vm_memory/volatile_memory/index.html).

### A02 — Snapshot capture is ordered before complete quiescence

**Where:** [park_for_snapshot](../../crates/vmm/src/vm/runtime.rs#L242), [coordinator barrier and write](../../crates/vmm/src/vm/runtime.rs#L564), [KVM save_state precondition](../../crates/vmm/src/hv/kvm/mod.rs#L376), [HVF interrupt state capture](../../crates/vmm/src/hv/hvf/mod.rs#L663).

A kicked vCPU calls `machine::capture` immediately, then records its captured state and parks. The coordinator waits for every captured slot and only then calls `bus.pause()`. The first CPU is therefore captured while another CPU can still run and device workers can still complete I/O or raise interrupts.

This directly contradicts the KVM save routine's requirement that every other CPU be stopped. It also captures HVF redistributor/ICC/power state before late changes from another CPU or an interrupt source. RAM, device queues, and global interrupt state are saved later. The resulting snapshot need not represent a coherent cut of the machine. An individual register round-trip test cannot detect that.

**Required change:** use a phased barrier: all vCPUs acknowledge leaving guest execution; device workers quiesce; each owning vCPU thread captures state; the coordinator saves global/device/RAM state; then resume or stop. Preserve HVF's thread-affinity requirement and ensure stop/error paths release every barrier.

**Validation:** snapshot with 2–64 vCPUs under IPIs, timers, block completions, and full-duplex vsock traffic; delay individual CPUs/workers at each barrier. Restore repeatedly and check pending interrupts, completed requests, and exactly-once workload effects. The bad ordering is source-proven; lost interrupts have not been reproduced in this audit.

### A03 — Snapshot publication is atomic per file, not per machine

**Where:** [write_durably, write, and read](../../crates/vmm/src/snapshot/mod.rs#L144); [daemon template publication](../../crates/shards/src/run.rs#L123).

The writer replaces `memory` before replacing `state`. If the second write fails, the existing state remains alongside the new memory. The reader validates memory length, not a shared generation. Two generations of equal-sized RAM are accepted as one snapshot. A reader racing a successful replacement can observe the same mismatch. Fixed `.memory.tmp` and `.state.tmp` names also allow concurrent writers to interfere.

**Reproduction:** write state generation 1 and RAM beginning with A; change to state generation 2 and RAM beginning with B; make `.state.tmp` a directory; call write again. It fails, but read succeeds with **state generation 1 and RAM B**:

    snapshot_failed_write=true read_accepted=true state_generation=1 memory_generation=B

The daemon's unique fresh template directory reduces exposure for first-time template creation. It does not make the public writer safe for directory reuse, direct `vm run --snapshot-dir`, or repeated snapshot requests.

**Required change:** store complete immutable generations and atomically publish one generation pointer/manifest. Pin that generation while reading both files. Include generation identity and structural integrity checks, use unique staging names, and fsync the relevant files and directory entries. A successful file rename is not a multi-file transaction.

**Validation:** inject failures after every write/sync/rename, race readers/writers, and retry interrupted saves. Recovery must yield the previous complete generation or the next complete generation, never a mixed pair.

### A04 — Running's destructor does not own shutdown or mapping lifetime

**Where:** [Running and wait](../../crates/vmm/src/vm/runtime.rs#L262), [launch's thread ownership](../../crates/vmm/src/vm/runtime.rs#L350), [arm64 RAM mapping contract](../../crates/vmm/src/vm/aarch64.rs#L176), [x86 RAM mapping contract](../../crates/vmm/src/vm/x86_64.rs#L203).

`Running::wait` stops and joins correctly, but Running has no Drop implementation and no requirement that callers invoke wait. Dropping its JoinHandles detaches the vCPU threads. Those threads retain Arc references to the VM and bus, so the VM can remain live after the Running value is gone.

For a plain machine without virtio devices or a snapshot coordinator, the bus/start state does not retain GuestMemory; the temporary VMGenId owner is also gone after launch. Dropping Running can release its final RAM owner while the detached vCPU still owns the VM mapping. This violates the explicit map_ram lifetime contract. With devices retaining RAM, the outcome can instead be a leaked live VM and workers.

**Required change:** make Running an actual RAII owner containing the stop handle and ordered teardown, or return one owning session whose Drop stops/joins before releasing VM/device/RAM mappings. An explicit asynchronous close may complement Drop, but error paths still need safe cleanup. A `must_use` annotation alone is insufficient.

**Validation:** start and drop a plain VM without calling wait, repeat with devices and snapshots, and inject failure after startup. Verify no live VM/thread remains and mapping teardown follows vCPU destruction. Do not rely on process exit to make the library API sound.

### A05 — Registry authentication crosses origin and TLS boundaries

**Where:** [Authorizer cache lookup and challenge](../../crates/registry/src/auth.rs#L217), [OAuth token POST](../../crates/registry/src/auth.rs#L360), [redirect handling](../../crates/registry/src/http.rs#L143), [URL authority/origin](../../crates/registry/src/url.rs#L108).

Two independently verified problems exist:

1. Challenge handlers are cached by `authority()`, without scheme. Default ports disappear from that representation. After an HTTPS Basic challenge for `registry.example`, requesting authorization for `http://registry.example` returns the cached credential. The direct registry-token path checks the scheme; cached Basic/Bearer handlers do not.
2. OAuth password/refresh-token secrets are placed in a POST body. HTTP follow preserves method/body across 307/308 redirects and applies no policy to the destination. Returning no Authorization header in its callback does not remove secrets from the body. Initial realm validation does not validate later hops.

**Reproduction:** the library returned an HTTPS-cached Basic header for an HTTP URL. A local token realm redirected a dummy password POST to a second loopback origin, which received the password and returned a token:

    cached_https_basic_attached_to_http=true
    oauth_redirect_completed=true cross_origin_received_password=true

The wire probe established a cross-origin body replay. HTTPS-to-HTTP OAuth replay is a source-proven consequence of the same unrestricted redirect path, not a separately exercised TLS connection.

**Required change:** key authorization by normalized scheme/host/effective-port origin, and introduce a redirect policy covering both headers and sensitive bodies. Reject TLS downgrade and unauthorized origin changes for credential-bearing exchanges. Permit legitimate registry-to-token-service relationships explicitly; do not grant every redirect destination that relationship.

**Validation:** Basic, Bearer, password OAuth, refresh-token OAuth, default/explicit ports, 301/302/303/307/308, same/different origin, TLS downgrade, and valid CDN blob redirects. Assert the destination receives neither header nor secret body when denied.

### A06 — Container visibility precedes ownership of its pending start

**Where:** [create before warm_for](../../crates/shards/src/daemon.rs#L555), [in-memory reservation](../../crates/shards/src/daemon.rs#L634), [busy release before track](../../crates/shards/src/daemon.rs#L421), [track insertion](../../crates/shards/src/daemon.rs#L736), [rm](../../crates/shards/src/daemon/commands.rs#L341), [await_exit](../../crates/shards/src/daemon.rs#L871).

The container is visible as Created before its warm VM is available. The separate runs map is populated only after handoff and after the Busy guard is dropped. Commands use that map to decide whether the container is running or has an exit to wait for. A successful remove during startup does not cancel the pending request; the request continues and executes. Later registry updates silently succeed when the removed record is missing.

**Reproduction:** delay VMM launch by two seconds, start a named container whose command exits 7, wait until `ps -a -q` shows it, then issue `wait` and `rm`:

    race_created_visible=True
    race_wait=0 wait_exit=0 rm_exit=0 run_exit=7 final_records=False

The workload ran after removal and left no container record. A Created container that never starts may legitimately yield 0 under the intended compatibility semantics; the defect is treating a committed pending start as though no execution could follow. The Busy-to-track gap additionally permits shutdown to observe no work before the handed-off run is registered.

**Required change:** give one lifecycle owner responsibility for Reserved/Starting/Running/Exited/Removing transitions. Register pending execution before publishing the container. Removal must cancel and wait for pending startup, or reject it; wait/stop/shutdown must observe pending starts. Transfer ownership atomically through handoff. Missing-record updates should expose an invariant failure rather than hide it.

**Validation:** deterministic barriers around reservation, warm acquisition, TAKEN, run insertion, STARTED, and DONE; race every management command and daemon stop through them. No successful removal may be followed by uncancelled execution.

### A07 — An unfinished client keeps daemon shutdown alive indefinitely

**Where:** [listen's quiet condition and take](../../crates/shards/src/daemon.rs#L346), [handle](../../crates/shards/src/daemon.rs#L462), [shutdown escalation](../../crates/shards/src/daemon.rs#L897), [await_exit subscriptions](../../crates/shards/src/daemon.rs#L874).

Every accepted same-user connection increments busy and receives a blocking thread. There is no initial-message deadline or connection admission cap. Shutdown stops known runs, but does not close/cancel these client reads. The exit condition requires busy to be zero.

**Reproduction:** connect to the private daemon socket without sending a header, then send STOP on another connection. The daemon was still alive a second later; closing the first connection immediately allowed clean exit:

    shutdown_with_incomplete_client_still_alive=True
    shutdown_after_client_closed_exit=0

This also affects build takeover and leaked client FDs. Identity checking occurs after receiving the message, so it cannot help. The peer UID check is useful authorization, but it is not admission control.

Timed-out waiters remain in the waiter list until the workload ends. Disconnected `wait` clients do not cancel their wait; a disconnected idle `logs -f` reader is only discovered when output is sent. These can retain busy threads and resources on long-lived containers.

**Required change:** bound initial IPC reads and concurrent work, track cancellation for accepted connections/subscriptions, cancel idle readers during shutdown, and remove abandoned wait registrations. Apply overall deadlines/cancellation to image preparation too; a per-read socket timeout does not bound a server that sends a byte periodically.

**Validation:** incomplete header/body/FD exchange, idle follower disconnect, wait disconnect, trickling registry response, and many simultaneous clients. Stop and takeover must finish within a documented bound without waiting for arbitrary clients to cooperate.

### A08 — A long log line is silently discarded as successful output

**Where:** [Line::send](../../crates/shards/src/daemon/commands.rs#L1083), [logs error handling](../../crates/shards/src/daemon/commands.rs#L580), [IPC payload cap](../../crates/ipc/src/unix.rs#L185).

Log frames are assembled into complete lines, but a complete line is sent as one IPC message. The payload cap is 1 MiB. Larger lines fail to send; logs converts that failure into status 0. Timestamp/detail prefixes can push a previously valid line over the cap.

**Reproduction:** seed an exited container with realistic 16 KiB log frames containing one line:

| Line/presentation | Expected | Actual stdout | Status |
|---|---:|---:|---:|
| 32-byte line | 32 bytes | 32 bytes | 0 |
| 1,048,577-byte line | 1,048,577 bytes | **0 bytes** | **0** |
| 1,048,576-byte line, plain | 1,048,576 bytes | 1,048,576 bytes | 0 |
| 1,048,576-byte line, timestamps | Line plus prefix | **0 bytes** | **0** |

This is realistic for minified JSON, base64, generated artifacts, and bulk output without newlines.

**Required change:** split output into transport-sized chunks while preserving stream identity and line-prefix semantics. Distinguish a client disconnect from an internal size/encoding failure, and return a failure when output was not delivered.

**Validation:** cap−1/cap/cap+1, much larger lines, final partial lines, both streams, timestamps/details, tail, follow, and broken clients. Compare exact bytes, not just exit status.

### A09 — Device draining is unbounded and can starve reset or other I/O

**Where:** [block stop/join](../../crates/vmm/src/devices/virtio/block.rs#L125), [block drain](../../crates/vmm/src/devices/virtio/block.rs#L227), [vsock loop](../../crates/vmm/src/devices/virtio/vsock/mod.rs#L335), [vsock TX-before-RX](../../crates/vmm/src/devices/virtio/vsock/mod.rs#L380), [pmem drain](../../crates/vmm/src/devices/virtio/pmem.rs#L206).

Block checks stop only outside drain, while drain processes until the queue stays empty. Vsock drains TX completely before RX, socket polling, expiration, or checking stop. Pmem processes the whole queue synchronously on a notifying vCPU. Ring size bounds the outstanding entries, not the number of entries a running producer can recycle.

A guest using another CPU to replenish a valid queue can prevent those loops from returning. Block reset joins the worker and can wait indefinitely; continuous vsock TX can starve RX/control progress; pmem notification can delay vCPU cancellation. The “stops between packets” description is not enforced by the worker loop.

**Required change:** bound requests/bytes per scheduling round, check cancellation between requests, deliver completed notifications at bounded intervals, and reschedule remaining work fairly. Preserve the TX-priority rationale for reply congestion without requiring TX to become empty. Re-arm queues carefully so budgeting cannot introduce a lost wakeup or busy spin.

**Validation:** continuously recycle descriptors while another vCPU resets the device or the host stops the VM; verify finite shutdown latency, RX progress, timer expiry, EVENT_IDX wrapping, no duplicated completion, and no missed re-notification. This scheduling defect is source-proven; a malicious SMP stress guest was not run.

### A10 — Digest-valid images can consume unbounded host resources

**Where:** [prepare's local max_layer](../../crates/shards/src/run.rs#L61), [pull's max_layer](../../crates/shards/src/pull.rs#L130), [layer accumulation](../../crates/image/src/layer.rs#L47), [rootfs construction](../../crates/image/src/store.rs#L460), [EROFS metadata construction](../../crates/image/src/erofs.rs).

Both production callers pass `u64::MAX` for the decompressed layer cap. Layer application keeps entries and a tree in memory; the EROFS writer materializes metadata. Superseded tree objects and concurrent preparations increase costs. Three simultaneous downloads are bounded **per pull**, not across the daemon.

A valid compressed digest and DiffID provide integrity, not a resource envelope. A compression bomb, enormous file tree/xattrs, many layers, or simultaneous image preparations can exhaust host disk/RAM/CPU before any VM memory limit applies. Image preparation runs with the user's host access.

**Required change:** enforce configurable per-image and aggregate budgets for compressed/uncompressed bytes, entries, xattr/path bytes, temporary disk, time, and concurrent preparations. Reserve budget before allocation/decompression and release it reliably on cancellation. Add per-ChainID construction singleflight; consider isolating expensive untrusted parsing in a restricted helper. Defaults should support representative large images while refusing unlimited consumption.

**Validation:** high-ratio compression, millions of tiny entries, replacement-heavy layers, large xattrs, malformed archives, concurrent same/different images, cancellation, ENOSPC, and constrained-memory execution. A refused image must leave no trusted partial rootfs or stranded budget.

### A11 — Cached configuration is neither rehashed nor validated like a fresh pull

**Where:** [local](../../crates/registry/src/pull.rs#L161), [fresh config/layer checks](../../crates/registry/src/pull.rs#L99), [Store::read](../../crates/image/src/store.rs#L405).

Local retrieval rehashes the manifest, then reads the config directly from its digest-named file. It does not recheck that config's digest/descriptor size. It also zips layer descriptors with DiffIDs without checking equal lengths; extra layers or DiffIDs can be silently discarded. Fresh pulls have the explicit count check, but also parse directly from the cached config file after fetch; verification should cover cached reuse on both paths.

**Reproduction:** create a valid cached image with Cmd `exit 7`; run it with `--pull never`; edit its stored config to Cmd `exit 9` without changing the digest filename or manifest; run again:

    config_original_exit=7 wrong_digest_accepted_exit=9 error=

This is an integrity/corruption failure. It is not claimed to grant additional privilege to an attacker who can already write the user's entire store.

**Required change:** read cached configs through the bounded verified-blob path and share semantic validation between fresh/local image construction: descriptor type/size, platform rules, rootfs type, layer count, and DiffID parsing. Keep the checks on small config/manifest data; do not blindly add full-rootfs hashing to every hot request.

**Validation:** change valid JSON under the old digest, truncate it, alter its size, and mismatch layer/DiffID counts. Local resolution must fail rather than execute a changed spec or quietly build an incomplete layer stack.

### A12 — Tail/follow memory use scales with the whole log

**Where:** [read before tail selection](../../crates/shards/src/daemon/commands.rs#L580), [Log::read and split](../../crates/shards/src/daemon/commands.rs#L1101), [record-write errors](../../crates/shards/src/workload.rs#L227).

`logs --tail 1` first reads the entire remaining file into a Vec, copies it into pending storage, and copies payloads into line buffers. Only then are earlier lines dropped. Even `--tail 0` incurs the initial scan/allocation. Concurrent readers multiply that working set. A line without a newline remains unbounded in partial storage.

Follow reopens/seeks/reads every 20 ms, approximately 50 polling rounds per second per idle follower. Log files also grow without a retention budget. Record write errors, including ENOSPC, are deliberately ignored so the workload continues, but the client/container receives no indication that logging has failed.

**Required change:** stream with bounded read buffers; use a reverse/indexed tail path and bounded line fragments; drive followers from append notifications with cancellation. Define retention/quota behavior explicitly and expose logging health/loss counters. Preserve output correctness through chunking rather than silently truncating long lines. Continuing a workload on log failure can be valid policy; representing its log as complete cannot.

**Validation:** multi-GiB logs with tail 0/1, hundreds of idle followers, long partial lines, log deletion, partial record writes, and ENOSPC. Measure peak daemon memory and idle CPU/syscalls; verify delivered bytes and surfaced failures.

### A13 — Per-template pools lack fleet resource ownership

**Where:** [daemon pool setting](../../crates/shards/src/daemon.rs#L270), [pool claim/refill](../../crates/shards/src/daemon.rs#L970), [state and quiet/idle condition](../../crates/shards/src/daemon.rs#L381).

Every template gets the configured ready count. There is no aggregate warm-VM cap, memory budget, or per-template aging/eviction. A continuously active daemon can retain two VMs for every image/guest/shape it has touched. One hundred templates imply two hundred idle VM processes plus their threads, FDs, private memory, page tables, and kernel virtualization resources. Disk templates/rootfs/blobs also accumulate.

The documented warm RSS is not a valid private-cost multiplier because snapshot pages are shared. The **unbounded number of retained VM owners** is nevertheless established independently of the exact memory accounting.

**Required change:** introduce global admission and memory/process/FD budgets; age or LRU-evict cold pools; adapt ready counts to observed demand and refill latency. Separate active execution capacity from speculation. Define disk GC with explicit roots for tags, templates, in-flight preparations, and running mappings.

**Validation:** repeated traffic through 1/10/100/1,000 distinct templates, bursts exceeding ready count, daemon idle/stop, and low host memory. Measure total fleet PSS/cgroup charge, kernel overhead, refill CPU, queue delay, and success rate. Never trade a tiny warm median for uncontrolled host pressure.

### A14 — A zero pool is accepted but cannot serve existing templates

**Where:** [setting parse](../../crates/shards/src/daemon.rs#L270), [claim and refill](../../crates/shards/src/daemon.rs#L970).

`SHARDS_POOL=0` is valid input to the current parser. The first run cold-boots and saves a template. Every subsequent claim finds no ready VM; refill computes zero work. The request waits until the 60-second deadline and fails.

**Reproduction:**

    zero_pool_first_exit=7
    zero_pool_second_exit=125 elapsed_seconds=60.07
    ... no warm VM ... was ready in 60s

**Required change:** either reject zero immediately with a clear configuration error or implement zero as “no speculative warm retention” with an on-demand restore. Validate very large and malformed settings as part of resource admission.

**Validation:** 0, 1, default, invalid/negative, and excessive values; repeated requests against both new and existing templates. There must be no configuration that starts normally and deterministically makes ordinary repeat execution time out.

### A15 — State mutation and persistence failure are not transactional

**Where:** [Registry reserve/update/save/remove](../../crates/shards/src/containers.rs#L134), [daemon record](../../crates/shards/src/daemon.rs#L890), [run_ended](../../crates/shards/src/daemon.rs#L840), [image store commit/replace](../../crates/image/src/store.rs#L93).

Container update mutates memory before writing the new record. Save writes and renames without syncing the file or parent directory. The daemon logs persistence failures and continues to acknowledge operation/state. Remove deletes the in-memory record before deleting its directory; deletion failure returns an error after runtime visibility has already changed. A restart can rediscover residual disk records.

Initial creation reserves only in memory. A crash before the first successful record write loses an already visible reservation; startup/handoff ordering compounds A06. Blob/tag and guest-file publication sync file contents in several paths but do not uniformly sync destination directories, so power-loss durability is weaker than “whole file + rename” may suggest.

**Required change:** specify the durability contract and acknowledgment points. Make failed removals retain a recoverable visible state; make failed saves explicit. For durable lifecycle claims, use a recoverable journal or ordered file/directory sync, with batching/group commit if necessary. Keep required correctness barriers even if measurement shows a latency cost. Do not move writes to unordered background tasks.

**Validation:** inject write/rename/delete/fsync failure and daemon crash at every lifecycle transition; restart and reconcile names, state, exit code, and cleanup. Separately test abrupt power-loss semantics on a suitable filesystem harness. Ordinary process-crash safety and power-loss durability are distinct guarantees.

### A16 — Snapshot working-set parsing trusts a huge count for allocation

**Where:** [working-set read/decode](../../crates/vmm/src/snapshot/mod.rs#L209), [Reader::seq](../../crates/vmm/src/snapshot/codec.rs#L127), [MAX_WORKING_SET](../../crates/vmm/src/snapshot/mod.rs#L32).

The working-set file is read with unbounded `fs::read`. Its sequence limit is 2^26 entries. Reader allocates capacity for the advertised count before checking whether enough encoded entries remain. A short file with a valid prefix and that count can request approximately **1 GiB of Touch capacity** before immediately failing on missing input. That capacity request is not a claim that every byte becomes resident.

The limit is unrelated to the snapshot's actual RAM/pmem page count. Invalid working sets are intended to degrade to an unprefetched restore, but an allocation failure can abort the process before that fallback.

**Required change:** cap file bytes before reading; verify count against remaining serialized bytes and the mapped address/page envelope before allocating; use fallible reservation and validate addresses/deduplication. Check recorded page size early. Update generic sequence decoding where element-size bounds are known.

**Validation:** a tiny file with huge count, truncated final entries, excessive valid files, duplicate/out-of-range GPAs, and mismatched page size. Invalid optional prefetch data must yield bounded work and a usable non-prefetched restore.

### A17 — Relative home paths are reinterpreted after chdir

**Where:** [home](../../crates/ipc/src/lib.rs#L16), [daemon initialization](../../crates/shards/src/daemon.rs#L240), [CLI home entry](../../crates/shards/src/bin/shards/client.rs#L238).

`SHARDS_HOME` is returned unchanged as a PathBuf. The daemon creates it, enters it, and then joins lock/PID/registry paths against the original relative path. Those paths now refer to a second nested location. The CLI's own directory changes can further reinterpret the same environment value.

**Reproduction:** run the daemon from a fresh directory with `SHARDS_HOME=relative-home`:

    relative_home_exit=1
    shards: relative-home/daemon.lock: No such file or directory (os error 2)

**Required change:** normalize the effective home to an absolute path once, before any chdir, and consistently pass that resolved value to descendants. Preserve the legitimate reason for a relative socket name: Unix-domain socket pathname limits.

**Validation:** relative home, absolute home, spaces, non-UTF-8 Unix paths, long home paths, and daemon auto-start from different working directories. Honor the XDG requirement for absolute XDG paths separately.

### A18 — Snapshot backing paths can resolve to different files on restore

**Where:** [machine configuration paths](../../crates/vmm/src/vm/aarch64.rs#L282), [x86 machine configuration](../../crates/vmm/src/vm/x86_64.rs#L321), [snapshot path encoding](../../crates/vmm/src/snapshot/mod.rs#L79), [disk/pmem CLI parsing](../../crates/shards/src/vm_run.rs#L178).

MachineConfig records caller-provided disk and pmem PathBuf values without resolving relative paths. Restore opens them relative to its current working directory. A snapshot restored elsewhere can fail to find backing files or bind a different same-named file. The codec also uses `to_string_lossy`, so a non-UTF-8 path supplied through the library cannot round-trip faithfully.

**Required change:** resolve backing paths at machine construction, or define an explicit snapshot-relative backing manifest and relocation procedure. Encode OS paths losslessly or reject unsupported representations before saving. Record enough backing identity to prevent accidental wrong-file restore while respecting the documented “backing file remains unchanged” contract.

**Validation:** save with a relative disk/pmem path, restore from another directory containing a same-named different file, and round-trip a non-UTF-8 Unix path. Verify both failure diagnostics and backing identity. Avoid hashing whole disks on every warm request.

### A19 — Kernel artifact identity omits compiler and linker inputs

**Where:** [kernel build script](../../scripts/build-kernel.sh), [toolchain installation](../../.github/workflows/kernel.yml#L31), [release tag calculation](../../.github/workflows/kernel.yml#L58).

Kernel source digest, configuration, and build metadata are pinned. GCC/binutils are installed from the runner's current apt repositories. The release identity hashes the script/config fragments, not the builder image, compiler, linker, or complete toolchain. Toolchain versions are recorded after building, but recording them is not pinning them.

Identical advertised input tags can therefore refer to different binaries on a later build. When the tag already exists, publication exits without comparing the new assets. Built-in download hashes protect consumers of the selected binary; they do not establish reproducibility of that binary from the documented tag.

**Required change:** pin a builder/toolchain by immutable identity and include it in artifact identity/provenance. Perform independent rebuild comparison and fail if an existing tag's outputs differ. Continue publishing kernel config, source digest, and checksums.

**Validation:** two clean builds on separate workers with identical declared inputs must match byte for byte. Changing the compiler/linker must change the input identity or be explicitly rejected.

### A20 — Spare creation has a check-then-publish race

**Where:** [make_spare and replacement threads](../../crates/shards/src/daemon.rs#L675).

Multiple refill/request threads can each observe no spare, release the mutex, create a directory/log, then overwrite the spare slot with their own result. The overwritten File closes, but its unused directory/log remains until later cleanup/restart. Under concurrency this converts a latency optimization into avoidable inode/disk churn.

**Required change:** reserve the “being created” state, or publish only if still vacant and delete a losing candidate. Preserve file creation outside the container registry lock.

**Validation:** run simultaneous makers behind a barrier; retain exactly one spare and no unreferenced directories. This is a cleanup defect, not a reason to discard pre-created log files.

The module design needs deeper ownership, not more generic wrappers. A stopped-machine capability should own snapshot invariants; a VM session should own mappings and teardown; a container execution should own all lifecycle states; an authentication origin/policy should own redirects; a fleet scheduler should own resource budgets. Repeated `unwrap_or_default`/ignored Results deserve targeted review where an invariant or delivery error is being erased. The proven examples are missing container records, logs output, and persistence. Replacing those with actionable errors is more valuable than a stylistic rewrite of every fallback.

## What it will take to substantiate the Firecracker goal

### Current evidence is promising but narrower than the goal

The comparison harness uses the same kernel/initrd/command line, interleaves VMMs, alternates order, and follows Firecracker's overhead rule. Those are good controls. The repository also documents failed optimizations, the earlier wait4 RSS mistake, and the crypto-selftest snapshot confounder rather than hiding them.

The latest recorded run at c7a3edd on a **nested Intel KVM CI runner** reports restore-to-beat medians of **7.377 ms for Shards versus 9.700 ms for Firecracker**, outside-guest VMM overhead of **2.8 versus 6.8 MiB**, and peak RSS of **21.2 versus 16.4 MiB**. Thus the observed restore is faster and the selected overhead metric is lower, while total per-process peak RSS is higher. These are repository observations, not a new audit run. [Recorded Firecracker comparison](../benchmarks.md#firecracker-cratesshardsbenchesfirecrackerrs).

The new anonymous/file-backed split is useful. The statement that each additional restored VM costs roughly 0.7 MiB plus page tables remains an extrapolation: RssAnon/RssFile alone do not measure proportional sharing, all host kernel/hypervisor charges, backing-page diversity, or multiple-template cost. Measure incremental fleet memory directly.

### Gaps that block a broad superiority claim

1. **Equivalent security work.** Firecracker runs with its default seccomp filters in the harness; Shards currently has no equivalent VMM syscall sandbox. Production Firecracker's jailer is also outside this benchmark. Report the exact configurations and measure a hardened Shards configuration. A comparison with fewer protections cannot establish the requested combined speed/correctness/isolation advantage. Firecracker installs filtering before guest execution and describes jailer-based production confinement. [Harness configuration](../../crates/shards/benches/firecracker.rs#L24), [Firecracker design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md).
2. **Pool refill is part of service cost.** The image benchmark executes a cold sample before its warm sample, giving the pool refill time. It excludes the first two or three unprefetched runs per template. This measures prepared steady behavior, not a burst, cold miss, changing workload, or arrival-rate service. Retain the diagnostic benchmark and add one that includes misses/refill/cancellation. [Image benchmark](../../crates/shards/benches/image.rs#L1).
3. **Tiny-sample p99 is fragile.** With 30 nearest-rank samples, p99 is the maximum. A 36% p99 difference in one such run is an observed maximum comparison, not a stable tail guarantee. Retain raw paired samples, repeat across hosts/runs, and report uncertainty and enough observations for the advertised tail.
4. **Account for the complete product.** Include daemon, ready VMs, starting/replacement VMs, clients, threads, FDs, page tables, hypervisor allocations, rootfs/snapshot cache, image preparation, logs, and disk retention. Report both fixed footprint and incremental cost per active/idle VM and per distinct image.
5. **Use matching endpoints.** Compare spawn→guest usable, request→actual workload exec, request→complete final output/status, and total lifecycle cost separately. A RESUMED marker or first beat cannot replace workload correctness and useful work.
6. **Separate hardware and configuration.** Run bare-metal x86 KVM as well as nested CI, multiple Intel/AMD hosts, 1/2/8/64 vCPUs, several RAM sizes, and realistic workload mixes. Mac HVF results are valuable product results but cannot alone establish a Firecracker comparison.
7. **Persist samples and enforce regressions.** Current harness output contains aggregate JSON, but CI does not upload a versioned raw-sample/resource artifact or impose a performance/correctness acceptance envelope. Capture source/guest/toolchain hashes, host/kernel/THP/security settings, dirty state, errors, timeouts, and load.

### Required benchmark matrix

| Dimension | Cases | Essential observations |
|---|---|---|
| Startup mode | Fresh process/VM; cold template; ready pool; exhausted pool | Endpoint latency, setup/refill work, misses, failures |
| Traffic | Sequential; synchronized burst; open-loop arrival ramp; overload | p50/p95/p99, queueing, throughput, deadlines, cancellations |
| Fleet | 1/10/100/1,000 VMs; 1/10/100 distinct images | Total/incremental PSS or cgroup charge, private/shared pages, page tables, kernel charges, idle CPU |
| Workloads | True/echo; build/compile; compression; large stdout/stderr; stdin; TTY; full-duplex vsock; block I/O | Exact status/output, completed work per CPU-second, I/O latency/bandwidth |
| Memory | Read-heavy shared pages; write-heavy COW; varied working sets; pressure | COW/private-page growth, fault tails, OOM behavior, prefetch waste |
| Host settings | Bare/nested KVM, Intel/AMD, varied THP, hardened configs, constrained CPU/RAM/FD/disk | Comparable security policy and reproducible host cost |
| Reliability | Reset/snapshot storms, crash, ENOSPC, client disconnect, signal races | No wrong output/status, finite cleanup, no leaks, safe recovery |

A useful acceptance target is a **Pareto improvement**: lower useful-work latency and lower total/incremental resource cost under the same protection and correctness envelope. Prewarming moves work earlier; it does not eliminate that work. The benchmark must charge it.

## Security and test coverage needed before release

The research correctly recognizes that a microVM boundary needs more than rootless execution. Current VMMs process guest-controlled structures with the invoking user's host privileges. Per-thread Linux syscall filtering, restricted filesystem/descriptor access, host resource policy, and a practical macOS containment strategy are still planned. This is a **known release requirement**, not an accusation that an already shipped sandbox regressed. The README's absolute “nothing inside one reaches your computer” language is stronger than the protection established by this implementation and audit. [Rootless security design](../research/rootless-security.md).

The larger shared-VM Engine will add a separate trust boundary between agents and init/engine. It needs its own namespaces, credentials, capabilities, filesystem/network/device policy, descendant ownership, quotas, and recovery tests. Do not extend the current single-workload proof to that architecture merely because both use Linux.

### Existing coverage worth preserving

- Real HVF guest boots/restores and image execution, not just mocked VMM tests.
- Snapshot register/state round-trips, entropy/clock behavior, private file mapping, virtqueue bounds, packet/connection tests, block/pmem integration, and layered EROFS semantics.
- Docker-derived flag/help/time/user behavior and CLI output fixtures.
- Locked Rust dependencies, immutable guest/kernel checksums, vendor checks, no-panic-oriented production lints, and an eight-target build/lint matrix.
- Explicit unsupported-feature handling and clearly documented backend limitations.

### Missing coverage and test infrastructure

| Area | Add | Why |
|---|---|---|
| Guest memory safety | Host alias/concurrency checks and stopped-memory ownership tests | Passing guest tests cannot establish Rust API soundness |
| Coherent snapshots | Multi-vCPU/device barriers, pending interrupts, repeated snapshots, failure injection | Register round-trips miss a machine-wide inconsistent cut |
| Lifecycle | A06's deterministic startup/removal/stop/wait/handoff barriers | Successful sequential management misses ownership races |
| Output | Exact byte checks for large/partial/interleaved streams, prefix boundaries, write failure | Exit-code-only checks miss silent loss |
| Authentication | Destination capture for headers and OAuth bodies across every redirect policy | Valid-token tests miss credential replay |
| Archive/rootfs | Fuzz/differential cases for tar/PAX/whiteouts/hardlinks/xattrs, quotas, malformed cache | Host parsers ingest remote and potentially adversarial data |
| Virtio/MMIO/vsock | Descriptor mutation/aliasing, recycling, EVENT_IDX wrap, reset storms, fairness | Per-chain bounds do not establish worker liveness |
| Persistence | Crash/fault recovery around every acknowledged transition and publication | Rename success is not equivalent to durable multi-object state |
| Fleet | Long soak with repeated image cardinality, overload, cancellations, FD/PID/memory pressure | A few successful runs do not establish density or cleanup |
| Backends | Dedicated KVM and HVF jobs that require guest execution | Compiling a target is not exercising its hypervisor |

The E2E helper's `cannot_run_vms()` returns a successful early exit after printing SKIP. That is appropriate on unsupported targets but weak on jobs intended to prove a functional backend. Add a **required-VM mode** on designated HVF/KVM runners that fails if virtualization is unavailable. Capture which VM cases actually ran. The Firecracker comparison job does require /dev/kvm access, which is stronger, but is not a replacement for explicit mandatory correctness coverage. [E2E skip helper](../../crates/shards/tests/common/mod.rs#L43), [CI matrix](../../.github/workflows/ci.yml).

Add bounded fuzz targets for the custom binary/text parsers rather than treating no-panic lints as a proof. Fuzzing should assert resource bounds and state transitions as well as “did not panic.” Retain crashing/minimized fixtures and fix the underlying invariant. Differential tests need explicit allowances for documented unsupported features.

Dependency provenance was verified offline against the two published archives. This review does not certify that the dependency graph has no current advisories. Add a maintained advisory check with documented exception expiry; keep vendor verification separate from vulnerability checking.

## Allocation, copying, retention, and page-fault continuation

### Checkpoint, method, and limits

This extension reviewed the current allocation paths across image preparation, daemon/CLI IPC, guest exec and relay, device queues and socket polling, memory mappings, snapshot codecs, and restore/prefetch lifetimes. Its checkpoint is **38457b7**, with source SHA-256 values recorded in the measurement artifacts. No product source was modified. It stays within Shards: the request to compare sibling QUIC/Raft products was retracted.

The new snapshot generation implementation fixes the original mixed-file publication problem; the working-set reader now checks counts against remaining bytes and the guest's page bound; backing paths are absolute and carry file identity; authentication is origin-scoped with restricted secret-bearing redirects. The kernel input now includes its pinned builder and DAX fix. These are material improvements. They do not close A01/A02/A04, establish fleet budgets, or make all later allocation failures recoverable. The current writer remains ROOTFS_VERSION 1 with regular-file inline tails; the separate plain-file DAX change is not in this checkpoint.

### A21 — Accepted RAM range ordering corrupts a save/restore round trip

**Priority/evidence:** P2, reproduced through the current public API. **Where:** [anonymous sorting](../../crates/vmm/src/memory.rs#L95), [file mapping](../../crates/vmm/src/memory.rs#L103), [save order](../../crates/vmm/src/memory.rs#L129).

`anonymous` accepts unsorted ranges, then sorts its region vector by GPA. `save` writes that sorted vector. `from_file` creates the same sorted memory but assigns file offsets while iterating the original input ranges. With equal-sized high/low ranges supplied in that order, a saved low=L/high=H becomes **restored low=H/high=L**. Current machine builders supply sorted ranges, so this probe does not demonstrate corruption of their existing CLI shapes.

**Required change:** normalize once and use exactly the same ordered region geometry for saving and mapping. Alternatively, reject unsorted inputs consistently and document that requirement, although accepting them in one constructor and silently reinterpreting them in another is unacceptable. Add regressions with unsorted, differently sized, noncontiguous ranges and compare every region's contents. [Durable probe](../research/measurements/audit-working-set/src/bin/range-order.rs), [observed bytes](../research/measurements/audit-working-set/range-order.json).

### A22 — A sparse save can leave previous target contents intact

**Priority/evidence:** P2, reproduced through the public API. **Where:** [GuestMemory::save](../../crates/vmm/src/memory.rs#L129).

Saving skips all-zero pages and only adjusts the destination length at the end. When an existing destination already contains nonzero bytes, skipped pages retain those bytes if the length stays the same. A subsequent restore therefore recovers obsolete data instead of current zero RAM. The new generation publisher creates fresh targets, so its current publication path is protected; this is a separate undocumented/unenforced requirement of the public save API.

**Required change:** require and verify a fresh/truncated destination, or clear it before creating sparse contents. Preserve the previous valid snapshot through the generation transaction rather than truncating a published file. Test replacement of nonzero pages by zeros in reused files, trailing zeros, multiple regions and failures. The memory corruption probe alongside A21 records this independently of any timing sample.

### D01 — Sparse saving visits every page and can materialize untouched RAM

**Evidence:** measured production API; high-priority cold/template resource opportunity. `GuestMemory::save` visits every host page and uses `chunk.iter().any(|b| b != 0)` to decide whether to write it. On this Mac, reading untouched anonymous pages materializes them. Sparseness of the output file does not preserve sparseness of the input's resident memory.

For **64 MiB of completely untouched zero RAM**, actual saving produced a 64 MiB logical file with **zero allocated data bytes**, made **zero Rust heap allocations**, but caused **4,096 minor faults and 64 MiB additional RSS**, with about 64 MiB additional physical footprint. At n=30, save time was **19.778/20.012/22.366/22.366 ms, p50/p90/p99/max**. With one nonzero byte per MiB already present, saving added the remaining **63 MiB RSS** and **4,032 minor faults**, while the sparse file allocated only 1 MiB. Its timing was **19.719/20.513/48.799/48.799 ms**. Round-trip page samples passed.

This is the memory scan/save alone, excluding CPU/device capture, publication and fsync. Do not extrapolate those milliseconds linearly to every guest size or to Linux. The daemon's first templated run resumes the original booted VM after saving, so newly materialized anonymous pages can remain charged throughout that first workload. [Cold-template resume](../../crates/shards/src/vm_run.rs#L213), [daemon cold selection](../../crates/shards/src/daemon.rs#L958).

There are two independent costs to attack: reading pages that are provably still zero, and inefficient zero detection on pages that must be examined. Evaluate word/SIMD zero checking under an enforced stopped-memory contract, preserving trailing bytes and every host-page boundary. A provenance bitmap could skip initially zero pages only if **every** host write, direct device read into RAM, atomic mutation and guest write is covered, and all CPUs/devices are quiesced. On a file-backed clone, complete dirty tracking could reuse immutable baseline bytes and overwrite dirty ranges. Charge tracking overhead and huge-page splitting. Fall back to the full scan if coverage is incomplete.

**Never use nonresidency/mincore as proof that a page is zero:** swapped/compressed or file-backed data may be nonresident. Blanket discard of RAM is also invalid. Consider a shared immutable zero backing or switching the first workload to a CoW restore only as measured designs with correct mapping invalidation, ownership, generation/clock behavior and teardown. A01/A02/A04 are prerequisites for such changes.

### D02 — Prefetch spends private pages; pre-reading does not eliminate CoW

**Evidence:** measured host CoW behavior plus existing guest-context research. For the same 64 MiB mapping, one byte per 16 KiB page gives:

| Host operation, warm backing cache | p50/p90/p99/max, ms | Median minor faults | RSS delta | Physical-footprint delta |
|---|---|---:|---:|---:|
| Read file pages | 2.201 / 2.316 / 2.526 / 2.526 | 4,096 | 64 MiB | about 48 KiB |
| Read and identically write each file page | 10.627 / 11.217 / 11.259 / 11.259 | 8,192 | 64 MiB | about 64 MiB |
| After a full read, identically write each page | 8.586 / 9.306 / 9.749 / 9.749 | another 4,096 | zero additional RSS | another 64 MiB |
| Read/write 64 pages, one per MiB | 0.183 / 0.223 / 0.410 / 0.410 | 128 | 1 MiB | about 1.047 MiB |

The backing file remained unchanged. Thus **64 identical one-byte stores can cost 1 MiB of private pages** on this host. RSS alone hides the conversion of already resident shared pages into private copies. Physical footprint here is process accounting, not a PSS or system-wide unique-page calculation. Apple documents MAP_PRIVATE's CoW semantics. [Apple mmap](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/mmap.2.html).

The implemented HVF prefetch deliberately touches recorded pages in guest context. It performs no-op writes for recorded written pages in writable RAM when FEAT_LSE is supported, and otherwise falls back to reads. KVM explicitly separates host CoW preparation with MADV_POPULATE_WRITE from nested mapping with KVM_PRE_FAULT_MEMORY, where supported; that ioctl prefaults as reads and does not itself break CoW. Host pre-reading is not a substitute for HVF guest-context prefetch: M5/M30 already tested that distinction. [HVF prefetch](../../crates/vmm/src/hv/hvf/mod.rs#L750), [KVM written-page preparation](../../crates/vmm/src/vm/x86_64.rs#L419), [KVM prefault API](https://docs.kernel.org/virt/kvm/api.html#kvm-pre-fault-memory), [research M30](../research/platform-measurements.md).

Use a fleet-wide **speculative private-byte budget** in addition to a page-count limit. Compare no/read-only/full/adaptive prefetch and charge every ready/replacement VM, including unused ones. Record touch-to-use ratio, written-to-actually-written ratio, unused-prefetch age, refill CPU and private-page growth for different commands using one template. An early workload's set is predictive data, not a guaranteed future set. Keep miss correctness independent of prediction. Never mutate logical bytes to manufacture a fast prefetch.

### D03 — Restore metadata is repeatedly decoded, expanded, and retained

**Evidence:** measured decoder expansion and source-proven lifetime retention. The new bounded reader is an improvement, but working-set wire bytes, decoded Touch objects and deduplication scratch coexist. Touch is **16 bytes**, although its wire entry is eight. Actual reading makes **four allocations, no reallocations**, with peak requested live bytes **32N+35** and returned capacity **16N**:

| Touch entries | Peak decoder heap | Retained Touch vector |
|---:|---:|---:|
| 718 | 23,011 bytes | 11,488 bytes |
| 3,867 | 123,779 bytes | 61,872 bytes |
| 65,536 | 2,097,187 bytes | 1,048,576 bytes |

More consequentially, `Shared` owns `Arc<Start>` and every vCPU closure keeps another reference throughout its execution loop. The measured arm64 VcpuState inline size is 896 bytes, excluding its heap vectors. [Shared lifetime](../../crates/vmm/src/vm/runtime.rs#L130), [vCPU closure](../../crates/vmm/src/vm/runtime.rs#L416), [release offset](../../crates/vmm/src/vm/runtime.rs#L175).

HVF also separately serializes code, page-table entries and addresses into temporary byte vectors before copying them into scratch RAM. KVM collects/sorts page vectors and builds runs for written-page preparation, then repeats that planning for nested prefaults. Parallel HVF helpers need explicit ownership of the fixed scratch GPA and a completion barrier before restoring state/unmapping it. The KVM pagemap recorder includes fault-around/host-device effects and scans logical RAM/pmem: it is a working-set approximation, not an exact guest-access trace. [HVF scratch construction](../../crates/vmm/src/hv/hvf/mod.rs#L781), [KVM run planning](../../crates/vmm/src/vm/x86_64.rs#L430).

Do not overstate present savings: M30's 718 entries are about 11 KiB, and M33's sets around 3,500–3,900 are about 55–60 KiB. Measure retained capacities by component, then consider immutable template metadata sharing per process where the backend allows it. The macOS one-VM-per-process constraint limits ordinary Arc sharing between pooled VMMs.

### D04 — Linux mapping policy loses advice and can charge full logical RAM

**Evidence:** source plus primary Linux accounting rules; Linux measurement still needed. `reserve_ram` aligns anonymous RAM and advises MADV_HUGEPAGE. `from_file` then replaces that mapping using MAP_FIXED|MAP_PRIVATE. The new mapping omits MAP_NORESERVE and does not inherit the anonymous VMA's huge-page advice. Alignment survives; the replaced VMA policy does not. [Reservation](../../crates/vmm/src/platform/unix.rs#L47), [private replacement](../../crates/vmm/src/platform/unix.rs#L113).

Linux accounts a private writable file mapping at its full size per instance. Consequently, 1,000 restored 256 MiB mappings can correspond to **250 GiB of commit accounting** even when most physical pages are shared. This is a theoretical accounting example, not measured fleet RSS or a demonstrated launch failure. Strict mode ignores MAP_NORESERVE. Define admission and commit policy deliberately; blindly adding that flag merely exchanges early rejection for possible later memory failure. Collect VmFlags, Committed_AS, CommitLimit, actual cgroup charge and launch errors under overcommit modes 0/1/2. [Linux overcommit accounting](https://docs.kernel.org/mm/overcommit-accounting.html).

Likewise, reapplying MADV_HUGEPAGE to a writable ordinary-file CoW mapping is not a promise of huge nested mappings. Anonymous THP, filesystem folios, host page-table entries, and KVM stage-2 entries are different layers. Avoid unnecessary placeholder reservation/advice work when the final backing cannot use it. Preserve M37's measured run-sized writes: they reduced nested faults versus per-page writes on the tested Linux hosts. Interpret older comparisons alongside M38's corrected crypto-self-test boundary. Test THP policy, filesystem, fragmentation, first-write tails and private amplification together. Larger pages reduce translation work but can waste memory for sparse access. [Linux THP](https://docs.kernel.org/admin-guide/mm/transhuge.html), [M37/M38](../research/platform-measurements.md).

NUMA first-touch placement and pooled-worker scheduling also need measurement on multi-socket hosts. Prefaulting everything from one refill thread may place useful pages far from the eventual workload CPU. Do not pin or spread blindly: compare local placement, shared-template locality and pressure. Linux-only facilities must remain behind platform/backend boundaries.

### D05 — Queue and packet metadata allocate per operation

**Evidence:** actual Queue allocation census and source packet tracing. A conventional three-descriptor request allocates a **64-byte** descriptor vector. For nonempty vsock data packets, the normal paths create:

| Path | Fresh metadata vectors | Payload behavior |
|---|---|---|
| Guest → writable host socket | Chain, payload spans, iovecs | Header copy; payload goes directly through writev |
| Host → guest | Chain, full-chain spans, payload spans, iovecs | readv fills guest RAM directly; header copy |
| Guest → backpressured host | Above plus TxBuf growth | Initialize buffered bytes, copy payload, later write |

Avoid reserving every theoretical maximum permanently in every queue. Preserve local descriptor copies: guest-controlled descriptor mutation makes borrowed chain metadata unsafe. Retain address/direction/aggregate-length checks, status-byte exclusion, indirect validation, atomic ring ordering and notification rechecks. Vectored positional block I/O needs correct short-I/O/offset/flush handling, not just fewer syscalls.

### D07 — Guest relay reallocates poll storage and repeatedly compacts streams

**Evidence:** source-extracted parser plus construction census. The relay builds `Vec::with_capacity(5)` each iteration, but full-duplex non-TTY operation can need **six** entries: SIGCHLD, host socket, pending stdin, signal socket, stdout, stderr. Its reproduced six-entry construction makes **one allocation and one reallocation**, requesting 40 then 80 bytes. A six-slot stack array with an explicit used count removes both; a reused bounded vector removes repeated construction. [Poll assembly](../../crates/init/src/run.rs#L807).

The larger cost is `each_frame` draining its Vec after every frame. A valid 65,535-byte input containing 5,461 twelve-byte signal frames and a three-byte partial header requires **178,918,743 suffix bytes** of compaction, calculated from the exact drain lengths rather than hardware copy counters. Actual parser p50/p90/p99/max was **1.670/1.708/1.800/1.903 ms** at n=500. A local cursor prototype shifts only the three-byte tail and measured **3.417/3.500/3.709/6.167 µs**. Both delivered every complete frame and retained the partial header. This is a control-heavy algorithm probe, not a measured guest relay speedup. [Prefix drain](../../crates/init/src/run.rs#L1000).

Parse with a head cursor and compact once per batch. Likewise, partial writes currently drain `to_host`/`to_stdin` prefixes; use offsets or a bounded ring. Consuming a 256 KiB backlog in 4 KiB pieces would move 7.875 MiB of suffix data with repeated drains. Regression requirements include every header/payload split, malformed framing, callbacks, coalesced control/stdin, short writes, EOF, HUP/ERR, ordering and independent signal readiness.

`BUFFERED = 256 KiB` is a readiness threshold, not a hard total allocation cap: a valid 1 MiB incoming frame can accumulate before dispatch, and simultaneously ready output pipes can append another pair of 64 KiB frames. Vec capacities retain high-water memory. Tightening budgets must use incremental parsing/backpressure while preserving accepted frames, not truncate them or deadlock on an incomplete frame.

### D09 — Credit bounds do not bound capacity; fragmented hostile chains waste work

**Evidence:** source-derived exact Vec growth and actual-device robustness probe. TxBuf permits at most 65,536 live bytes, but resizing from 65,535 to 65,536 grows capacity from **65,535 to 131,070** on this toolchain. A maximum-fanout set of 1,023 such buffers corresponds to roughly **128 MiB of requested capacity**, before socket/kernel memory. Indirect traversal accepts up to global MAX_CHAIN=4,096 even for the 256-entry vsock queue. Kernel loading already uses direct positioned reads into paused RAM; adding an intermediate kernel Vec is a regression. Remapping the kernel file is also not a free improvement: M16 records serious first-touch stalls. This work affects cold boot/template preparation, not an already prepared warm run. [arm64 kernel load](../../crates/vmm/src/arch/aarch64/boot.rs#L114), [M16](../research/platform-measurements.md).

### D14 — Density needs ownership budgets and pressure measurements, not an allocator swap

The best initial allocation changes remove repeated work or release dead ownership: historical log buffers, one-shot restore state, tiny-frame compaction, readiness setup, inode/tail/header temporaries. A replacement malloc may change size classes or contention but cannot fix those algorithms or create a fleet budget. Benchmark alternative allocators only after an allocation census of the full daemon/VMM/guest path, including idle retained memory, burst peaks, cross-thread frees and recovery after load.

Budget **capacity** as well as lengths; account for all warm, active and replacing VMs, distinct template/page-cache sets, log followers, image preparation, native TLS/decompression state, threads/stacks, FDs and hypervisor/kernel memory. A 1 MiB application buffer, thousands of tiny metadata allocations, and a 1 MiB shared file mapping have different density effects. Logical reserved RAM and peak RSS alone cannot settle the target.

For Linux, report PSS/private/shared breakdown and cgroup charge including kernel/page tables, mapped file-cache sharing, host overcommit/THP policy and NUMA placement. For macOS, combine mapping/footprint accounting with supported guest-context measurements, and measure the full set of processes plus backing-cache diversity. Record pressure, swap/compression, cache-hot/cache-cold state and end-to-end fault tails. Native allocation counts miss guest-context costs.

Do not add unconditional preallocation, mlock, huge pages, userfaultfd restore, KSM, discard, or compression because they improve a single median. Each needs its own measured CPU/private-memory/tail tradeoff and correct failure behavior. File-backed immutable snapshots already provide sharing; KSM scans anonymous pages and spends CPU/metadata, rather than deduplicating existing file-cache pages. [Linux KSM](https://www.kernel.org/doc/html/latest/admin-guide/mm/ksm.html). Prefer explicit shared immutable ownership before background deduplication.

Acceptance should require exact bytes/status/filesystem behavior, no new aliasing or snapshot inconsistency, bounded cleanup under cancellation/reset, and better useful-work latency **and** total resource cost at the selected fleet/workload envelope. Add phase allocation/realloc/copy counts and host/guest fault counters to the existing benchmark matrix, then evaluate improvements one at a time with raw paired samples. Prewarming/early CoW should be charged as service work, even if it disappears from request latency. After the pending memory Access work is correct and integrated, measure its lock contention across SMP/device workloads; keep blocking I/O outside unnecessarily broad guard lifetimes and retain the synchronization proof when narrowing them.

Apply this order to remaining findings; retain regressions for concurrently closed items in the response tracker.
