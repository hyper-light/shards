# shards 0.8.0

Windows on arm64 now runs microVMs: `shards-windows-arm64.exe` boots, saves and restores
them through the Windows Hypervisor Platform. Live moves now work on x86_64 Windows. A
Windows Server host that allows device assignment can give a microVM one of its PCI
devices. Builds held to a memory limit now write their files outside that limit, which
0.7.0 was meant to do and did not.

## New

### Live moves on Windows and arm64 Linux

`shards move vm --live NAME CONTEXT` is no longer refused on Windows or on arm64 Linux. On
x86_64 Windows, live moves pass shards' move tests on CI's Windows Server 2025 runners,
between two homes on one machine, including a microVM that keeps writing its memory while it
moves and loses none of it. On arm64 Linux and arm64 Windows, live moves are built but have
not yet been run with real microVMs.

Each hypervisor now reports what the guest writes during a move: KVM's dirty-page bitmaps
on arm64 (the bitmap also catches what the interrupt controller writes into guest memory),
and the hypervisor's own dirty-page tracking on Windows. x86_64 Linux kernels older than
5.11, which have no dirty rings, use the same bitmap.

### PCI devices on Windows Server

Where Windows' hypervisor allows device assignment (Discrete Device Assignment: Windows
Server on hardware with an IOMMU), a microVM's kernel can be given a PCI device that you
have dismounted from the host with `Dismount-VMHostAssignableDevice`:

```console
> shards run vm --kernel vmlinux --vfio 'PCIP\VEN_...' ...
```

Name the device by the instance ID `Get-VMHostAssignableDevice` lists. The host's IOMMU
limits its DMA to the microVM's own memory. This works the same way on x86_64 and arm64
Windows. Every Windows host tested so far refuses device assignment, and shards passes on
their answer.

The device is given as the microVM starts, and goes to the microVM's kernel only:

- A program in the microVM can't be given one on Windows (`--device`, `plug function`),
  because the hypervisor gives the guest no I/O address space of its own, which handing a
  device on to a program needs.
- A device can't be plugged into a microVM that is already running on Windows. Microsoft
  documents device assignment only for a VM that is given its device before it starts, and
  shards now says so instead of trying.

### Hard links from Windows clients

When you build or `cp` from a Windows machine, files with several names now arrive as hard
links, as they do from macOS and Linux. Before, a Windows client sent the whole file again
for each name. Docker's Windows client still does that. The archive a Windows client sends
is now byte for byte what a Unix client sends for the same tree.

## Platforms

### arm64 Windows

On arm64 Windows 11 (24H2, build 26100.3915 or later) with the Windows Hypervisor Platform
turned on, `shards` runs microVMs. It uses the same daemon, images, volumes, networks and
snapshots as the x86_64 build.

- Snapshots keep every vCPU's registers and the interrupt controller's state. A restore
  holds the guest's clock until its vCPUs run again, so the guest's time never jumps.
- A restore maps the pages the microVM's start touched before the guest needs them, as on
  x86_64 Windows.
- On a machine without the Windows Hypervisor Platform, `shards` says "no hypervisor runs on
  this host". Before, it gave an error about a missing device.

So far this has been tested on Windows 11 Pro arm64 running emulated on a Mac, with Windows'
own hypervisor ([PM M414](https://github.com/hyper-light/shards/blob/v0.8.0/docs/research/platform-measurements.md)). There, shards booted its
kernel as a standard user, and restored three separate processes from one snapshot. Busy
microVMs of 2 and 8 vCPUs went on past their snapshots and restores with their clocks and
interrupts intact. The whole test suite has not passed there yet (see Known limits).

CI now builds arm64 Windows on arm64 Windows runners and runs its tests there. Those runners
have no hypervisor, so their microVM tests are skipped.

### x86_64 Windows

0.7.0's notes said `plug volume` was refused on Windows and `plug disk` was untested there.
Both work. These now pass with real microVMs on CI's Windows Server 2022 and 2025 runners,
where every microVM test must run:

- `shards plug` and `unplug` for disks and folders, and `shards grow disk`
- saved and live moves between homes, with a volume's owners, modes, symlinks and device
  nodes kept
- restarts that reuse a stopped microVM's kept writable layer

Of the 129 build tests, 125 now build for Windows and run there. Before, the whole set was
Unix-only. The build context tests, which hold what a build sends to what buildx sends,
and the test of a kept `.git` directory now run on Windows too, against what buildx's own
file walker records on Windows.

### Linux

- `shards plug function` now passes nested on arm64 Linux (an M5 Max), for a program that
  doesn't run as root, with the device named by its PCI name or by its VFIO device node
  (`/dev/vfio/devices/vfioN`) through iommufd.
- The VMM's part of plugging a host's PCI device took 602 µs at p50 and 626 at p90 (n 30,
  nested arm64 KVM on an M5 Max). The first plug into a microVM took 170 ms: VFIO pins all
  of the microVM's memory for the device, and memory the microVM hasn't touched yet has to
  be faulted in first. A microVM booted with a device pays the same cost as it starts
  ([PM M430](https://github.com/hyper-light/shards/blob/v0.8.0/docs/research/platform-measurements.md)). The whole command hasn't been timed
  yet.

### macOS

Nothing in this release is macOS-only. The context fixes and the faster policies apply
there too. CI's macOS runners have no hypervisor, so macOS is tested with real microVMs on
Macs outside CI.

## Faster

- **Build policies** (`--policy`, `buildx policy eval`, `policy test`) with many rules
  compile faster. A 6,000-rule policy parsed and compiled in 299.8 ms at p50 (p90 308.6, max
  313.8), down from 779.5 ms (p90 807.0, max 825.2). A test of a deeply nested `every`
  policy took 1,736 ms at p50, down from 3,372 ms. These were measured on an M5 Max with
  macOS 26.4.1, n 30 and n 20, the builds alternating
  ([PM M414](https://github.com/hyper-light/shards/blob/v0.8.0/docs/research/platform-measurements.md)).
- **Folders shared from Windows** no longer copy a directory's whole listing into memory
  each time a program in the microVM opens the directory. Before, 100 open directories of
  2,000 entries each held 10.77 MB on CI's Windows Server 2025 runner. Each open directory
  now keeps Windows' own handle to it and at most one 4 KiB batch of entries.
- **`shards inspect`** with many names reads the image store once per command instead of
  once per name. How much time this saves has not been measured.

## Changed

- **A slow start is waited for.** On a slow or very busy host, a microVM that is still
  booting after a minute is no longer given up on. The daemon checks each starting microVM
  every 10 s. It gives up only after a minute in which the microVM used no more CPU than an
  idle one. A microVM that never runs is still given up on a minute after it starts.
  Builds' microVMs are judged the same way. On an emulated arm64 Windows host, every
  microVM that had been given up on was still booting
  ([PM M424](https://github.com/hyper-light/shards/blob/v0.8.0/docs/research/platform-measurements.md)). The daemon's log, `daemon.log`, now
  records every 10 s how much CPU each busy microVM that a client is waiting on has used.
- **`shards configure disk`** is refused through a context. The share of the machine's
  disk that shards keeps is the machine owner's to set, as `configure guest` already was.

## Fixed

- **Builds held to a memory limit** (Linux). In 0.7.0 the process that should write a
  limited build's files outside its limit was refused as an unknown command. The build then
  wrote its files itself, inside its limit, and its writing steps were slower. On CI's
  runners, the end of an `apt-get` step took 4.3 to 10.9 s with a limit, against 2.6 to
  4.4 s without one, while `apt-get` itself was no slower. Now the writer runs. A step's
  changes go to it a chunk at a time instead of one message per file, and a cache's merged
  layers go through it too. After those fixes, builds with a limit were no slower than
  builds without one in 11 of CI's 12 runner and build pairs. What was left, on every
  runner, was writing the image: 0.21 to 0.29 s longer at the median with a limit. Writes
  now pass to the writer through memory the build and the writer share, which is meant to
  remove that difference. This last change has not been measured yet
  ([PM M442](https://github.com/hyper-light/shards/blob/v0.8.0/docs/research/platform-measurements.md)).

- **Contexts.** A command run with `--context default`, under a `SHARDS_CONTEXT` or
  `DOCKER_CONTEXT` naming another machine, or in a home whose current context is another
  machine, sent shards' own helper processes to that machine. So its daemon never started
  here, and a macOS `restore`'s grants broker, a Linux restore's working-set writer and an
  image's SBOM build were sent to the other machine. Shards' own
  helpers now always run on the machine that starts them.
- **A build context changed while it is sent.** If a file or directory in a build's
  context was replaced by a symlink after shards had listed the context and before it sent
  it, the build could send files from outside the context. Each directory is now opened
  inside the one above it and never through a link, on every platform, and a file a link
  replaced is refused. On Windows, unpacking files onto the host (`cp` out of a microVM,
  a build's output to a directory) now does the same, so a directory swapped for a link during the unpack is not followed
  out of the destination. buildx follows such links, so here shards differs from Docker on
  purpose.
- **Removing a context.** Once `shards remove context` returns, nothing more reaches that
  machine through the context. Before, the daemon could make the context's socket again
  for a moment and pass on a client that had connected just before the removal.
- **PCI devices for programs that don't run as root** (Linux). A device plugged into a
  running microVM now belongs to the user the program runs as (its `--user`, else its
  image's `USER`), and so does `/dev/iommu` while the device is plugged. Before, a
  program run as the image's own user got "Permission denied".
- **Windows:**
  - AWS credentials from a `credential_process` command work when the command holds JSON
    or quotes, or its program's path has spaces.
  - `SHARDS_CDI_SPEC_DIRS` is split at `;`, as Windows lists paths. Before, a drive's path
    was broken at its `:`, and CDI devices in builds were missing.
  - Messages about a Dockerfile's own policy name it `Dockerfile.rego`, as buildx does on
    Windows, not `.\Dockerfile.rego`.
  - A build context's symlinks that a build follows (`COPY` of a link) resolve as buildx
    resolves them on Windows: a link to `/etc/hosts` is taken from the link's own
    directory, as Go's Windows paths have no drive there, and a name Windows can't hold
    names nothing.
  - A microVM's vCPU threads that run in short bursts keep their raised priority. Windows
    counts CPU time in 15.6 ms ticks, which had sometimes dropped such a thread to normal
    priority for 100 ms.
- Many intermittent test failures on CI's Windows runners and on the emulated arm64
  Windows host were traced to their causes and fixed.

Runs boot the same pinned kernel as 0.7.0, `kernel-6.18.48-64a9427a8997`.

## Known limits

- **arm64 Windows**: the full test suite has not passed yet. Qualification is in
  progress, so far only on an emulated host, where microVMs of 64 vCPUs on its 4 CPUs run
  very slowly ([PM M427](https://github.com/hyper-light/shards/blob/v0.8.0/docs/research/platform-measurements.md)). It has not yet been run on
  arm64 Windows hardware. GPUs haven't been tested there, and a host's PCI device given to
  a microVM there is built but untested, as on x86_64 Windows.
  <!-- PENDING: step 10 qualification. If the full real-VM suite passes on arm64 Windows

- **Live moves** on arm64 Linux and arm64 Windows have not been run with real microVMs yet.
  How long a live move on Windows stops its microVM has not been measured. A volume's files
  are still sent with the final pass, so large volumes lengthen the time the microVM is
  stopped.
- **Moves between two machines.** Every move tested and measured so far, saved or live, has
  been between two homes on one machine. Moves between two machines are built, and a
  harness for them is ready, but none has run yet.

- **PCI devices.** Windows' device assignment, on x86_64 and arm64, is untested on hardware
  that allows it, and so is whether the microVM's sandboxed process may claim the device
  there. On Windows a device can't be plugged into a running microVM. Linux's on x86_64
  has been tested only with an emulated test device. Devices whose memory sits above 4 GiB
  can't be plugged yet. A plugged folder can't use the page-cache sharing that folders
  given at start use. macOS offers no device assignment at all.
- **Restarts that reuse the kept layer** haven't been run with real microVMs on a Mac yet.
  On Windows, how they compare with copying the layer hasn't been measured.

- **IPv6**: name lookups and published ports still reach agents over IPv4.
- **GPUs on musl** use Mesa's drivers only: NVIDIA ships no driver for musl.
