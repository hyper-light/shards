# shards 0.8.0

MicroVMs now move between machines: between two wired Linux machines a live move stopped
its microVM for 0.21 s at the median, and a CPU baseline is there for machines whose CPUs
differ. Windows on arm64 runs microVMs. Through a context, the folders you bind are your own
machine's, and the other machine's folders, devices and GPUs reach you only as its owner
grants them. Programs that run agents can boot and drive shards microVMs themselves, holding
each agent's input, output, terminal and network reach. Intel Macs are no longer a release
target: this release has seven binaries.

Download `shards` for your machine below and check it against `SHA256SUMS`, as the
[README](https://github.com/hyper-light/shards#install) shows. It is still the only file to
install.

Each item ends with where its evidence is: D-numbers are decisions in
[architecture.md](https://github.com/hyper-light/shards/blob/v0.8.0/docs/design/architecture.md),
M-numbers measurements in
[platform-measurements.md](https://github.com/hyper-light/shards/blob/v0.8.0/docs/research/platform-measurements.md),
and the hex numbers the commits on `main` that made the change.

## New

### Moves between machines

`shards move vm NAME CONTEXT`, and `--live`, now hold up between two machines, not only
between two homes on one machine.

- **Measured between two wired Linux machines** (x86_64, KVM, a gigabit link, n 20 of each):
  a cold move of an alpine microVM left it running nowhere for 0.91 s at the median (p90
  1.12 s), a live one for 0.21 s (p90 0.28 s, at most 0.35 s), in two or three rounds. 40
  of 40 moved. The first move into a fresh home left its microVM running nowhere for 9.9 s,
  as that home fetched the image (PM M497).
- **A move's stream is compressed to suit its link.** It goes in 1 MiB frames, each
  compressed with zstd where that makes it smaller. The level goes up while the move waits
  on the link, and down while it waits on compressing. Between two homes of a Mac Studio, a
  cold move's 82 to 84 MB stream went as 21 to 33 MB. A machine running 0.7.0 is sent the stream uncompressed (D176 part 6, PM M462;
  65e3f462).
- **A live move stops copying once its rounds stop shrinking**: at the first round that is
  no smaller than the one before, as well as at a round of 8 MiB or less, after three times
  the first round's bytes, or at 30 rounds. Before, a live move over Wi-Fi of a guest that
  kept writing had not finished after 30 minutes (D176 part 7; 65e3f462).
- **A connection stays open while the other machine is still heard.** An established
  connection now ends after 100 s with nothing heard from the other side, not 10 s.
  Connecting to an address where no daemon answers still fails after 10 s (D176 part 6;
  65e3f462).
- **A fresh home fetches the kernel and init as it readies**, before the stream. A fresh
  home's first move had left its microVM running nowhere for 40.7 s, 28.7 s of it a restore
  waiting on that download (PM M462; 20f080a4).
- With `SHARDS_MOVE_TIMES` set, each move reports what it sent, how much of it was
  compressed, the link's rate and its longest silence, and for a live move each round's
  bytes and why the rounds stopped (D176 parts 6 and 7; 65e3f462).

### A CPU baseline for the machines you move between

A microVM resumes only on a machine whose CPU has every feature its guest found. Between an
M3 Ultra (macOS 26.4) and an M4 Max (macOS 26.2), 38 of 40 moves were refused, as each has
features the other lacks (PM M462). `shards configure cpu --baseline CONTEXT[,CONTEXT...]`
asks this machine and each context's machine for the CPU its hypervisor shows a guest, and
tells every microVM this home starts only what all of them have. `shards inspect cpu` shows
it, and `--none` takes it away. Built on macOS and on x86_64 and arm64 Linux, and tested on
a Mac between two homes, where the baseline was all the guest found and went with it when it
moved (PM M497, M499). On x86_64 Windows a move checks the other machine's CPU first, but a
baseline isn't built there yet (D245; 4a8dbf2cc, f617f36e7, 4615b2d77, 0551545cc).

### Live moves on Windows and arm64 Linux

`shards move vm --live NAME CONTEXT` is no longer refused on Windows or on arm64 Linux. On
x86_64 Windows, live moves pass shards' move tests on CI's Windows Server 2025 runners,
between two homes on one machine, including a microVM that keeps writing its memory while it
moves and loses none of it. Each hypervisor now reports what the guest writes during a move:
KVM's dirty-page bitmaps on arm64 (which also catch what the interrupt controller writes into
guest memory), and the hypervisor's own dirty-page tracking on Windows. x86_64 Linux kernels
older than 5.11, which have no dirty rings, use the same bitmap (D176 part 7; d084848df,
c74e18bd5).

### Your own folders through a context

Through a context, `-v` and `--mount type=bind` now bind the folder on the machine where you
typed the command, served from there, relative paths from your working directory, as a bind
of a local folder behaves. `shards plug volume` through a context plugs your folder the same
way. The other machine's own folders, devices and GPUs reach a client only as that machine's
owner grants them: `shards grant client NAME --dir PATH[:ro] --device NAME --gpus`,
`shards revoke client NAME ...` and `shards inspect client NAME`. Over loopback, opening,
reading 4 KiB and closing a file through such a bind took 251 µs at the median against a
local bind's 136, a 64 MiB read ran at 458 MiB/s against 468, and a write at 572 MiB/s
against 2,157 (D228, PM M511; ea34aa231, 5a936953d, 703c6a069).

### Commands

- `shards attach vm NAME`, `shards update vm NAME --cpus N --memory SIZE ...`,
  `shards wait vm NAME` and `shards import vm|image FILE|URL|- [NAME]`: every command a
  microVM needs now has a form of shards' own, and `shards vm ls`, `shards vm rm` and the
  rest are read turned round, as Docker's `image ls` is (D216; 9d03f9a3d).
- `shards read metrics MICROVM` prints a microVM's metrics as an OpenTelemetry request
  (OTLP JSON): CPU, memory, tasks and block I/O of its run, of its workload and of each agent
  and harness, read when you ask, with nothing left running to collect them (D61;
  a920c85b5).
- `shards exec vm --for MEMBER NAME COMMAND` runs a command inside one agent or harness, as
  that member runs: its user, namespaces, cgroup, Landlock rules and seccomp filter. What
  the member may not do, the command may not either (D243; 3fe2c9db5, a5a92211f).
- `shards plug volume NAME SOURCE:PATH[:ro] --for MEMBER` plugs a folder into a running
  agent or harness at the path you name. Names that differ only in case are handled on
  macOS and Windows, and edits made on your machine wake programs in the microVM that watch
  with inotify (D235; 03cb7c54e, c654d53a3).
- The Engine API's stats now carry each vCPU's guest time beside the VM process's CPU time,
  in their `microvm` object, read from each hypervisor (D43; 221c73774, 6396a78b8).
- Every microVM shards makes, from a run, `create`, a tag, a commit, a load or a build,
  appears in Docker's image store as `shards.local/NAME`, as pulls and imports already did
  (D216; 9d03f9a3d).

### Agentfiles

- **Destinations by name.** A network's egress can name the hosts its members reach:
  `NETWORK --egress=HOST:PORT`, a host's name or an IPv4 address, or
  `host.docker.internal` for your own machine at that one port. Members resolve those names
  alone and reach nothing else on that port (D236; 98921fd80, 6576aca74):

  ```dockerfile
  HARNESS codex FROM ./codex
  NETWORK --egress=api.openai.com:443 --egress=chatgpt.com:443 provider FOR codex
  EXPOSE --harnesses=codex 443 AS egress FOR provider
  CONNECT codex WITH codex ON provider
  ```

- **`EXPOSE ... FOR`** may name agents and harnesses as well as networks: the port opens for
  that member alone (D122; 582d90444).
- **`NESTING`** lets an image's own command make boxes (containers, sandboxes) inside its
  microVM, where the run asks for it too (`--security-opt nesting=true`). It is never granted
  beside an agent or harness, and is checked when the image is built and again when it runs
  (D234; b3001d90a, 3ab1eab5d, 9c886608d).
- **Agents and harnesses start as programs expect**: with the image's `ENV`, the run's
  environment, a private writable `HOME` and the working directory the run names. A
  harness's stdin is a stream its owner holds, byte for byte, with its end and abort
  (D240; 239749c60, ac9bb8589, d6ac7e48f, e7825cb32).

### For programs that run shards

`shards-api` (`crates/api`) lets a program boot microVMs through the `shards` binary and talk
to them, every refusal typed (D215, PM M463, M464, M465, M515; 86b4422cb). With it, a
program can now:

- boot an Agentfile's image under shards-init with no daemon, one `shards` process hosting
  each run (D231; 6aa822fef);
- hold each agent's and harness's stdin, stdout and stderr, give it a terminal of its own and
  size it, and exec into it (D240, D243, D244; e7825cb32, d689fa652, c2ecd9e81);
- keep or drop each member's network destinations before the microVM starts (D246;
  7a4ef5c02);
- tell a run the room its budget leaves it, and read its microVM's cost in its stats (D241;
  3ce473b31);
- give a microVM GPUs by their exact identity: a PCI address, a Metal registry ID, or this
  boot's DXGI LUID on Windows (D232; 08bb8fda1, 1fd078bfb);
- start the VM process itself, inside its own cgroup or Job object (D233; 84274050f,
  301e5bddb);
- carry `shards` inside its own binary, `shards` writing its VM and network processes out
  beside the copy, signed as the program signs its own (D237; f2a42e98a, d42407036);
- reach a microVM's members over one encrypted connection whose TLS ends at the host: their
  stdio as lanes, and execs (D238, PM M540; 2a3b62356, c9630c6b4, 4c50a8744, cf9e4590b,
  f0a651428, cc36a60d3);
- name a credential without ever putting it in the microVM: the contract is built, the
  parts that fill it in at the microVM's egress are still to come (D242; 485fe0c21).

vsock connections are now credited before they run out, and lent a window of up to 4 MiB
where their guest uses it (D12; 1e448c7ec, b1a011876). Moving a microVM's engine connection
from vsock to a ring in its guest's memory has begun: its first steps are in, and its tests
on real microVMs haven't run yet (D230; 261412b01, 032b63b1c). What either gains is not in
the measurements record yet.

## Platforms

### arm64 Windows

On arm64 Windows 11 (24H2, build 26100.3915 or later) with the Windows Hypervisor Platform
turned on, `shards` runs microVMs. It uses the same daemon, images, volumes, networks and
snapshots as the x86_64 build.

- Snapshots keep every vCPU's registers and the interrupt controller's state. A restore
  holds the guest's clock until its vCPUs run again, so the guest's time never jumps.
- A restore maps the pages the microVM's start touched before the guest needs them, as on
  x86_64 Windows.
- On a machine without the Windows Hypervisor Platform, `shards` says "no hypervisor runs on
  this host". Before, it gave an error about a missing device.

So far this has been tested on Windows 11 Pro arm64 running emulated on a Mac, with Windows'
own hypervisor (PM M414). There, shards booted its kernel as a standard user, and restored
three separate processes from one snapshot. Busy microVMs of 2 and 8 vCPUs went on past their
snapshots and restores with their clocks and interrupts intact. The whole test suite has not
passed there yet (see Known limits). CI builds arm64 Windows on arm64 Windows runners and runs
its tests there; those runners have no hypervisor, so their microVM tests are skipped
(D209, PM M423; cdd2c031f).

### Windows

- **PCI devices on Windows Server.** Where Windows' hypervisor allows device assignment
  (Discrete Device Assignment: Windows Server on hardware with an IOMMU), a microVM's kernel
  can be given a PCI device you have dismounted from the host with
  `Dismount-VMHostAssignableDevice`, named by the instance ID `Get-VMHostAssignableDevice`
  lists: `shards run vm --kernel vmlinux --vfio 'PCIP\VEN_...' ...`. The host's IOMMU
  limits its DMA to the microVM's own memory, on x86_64 and arm64 alike. Every Windows host
  tested so far refuses device assignment, and shards passes on their answer. A device can't
  be handed on to a program in the microVM on Windows (`--device`, `plug function`), nor
  plugged into a microVM already running: Microsoft documents assignment only for a VM
  given its device before it starts (D154, D214; 9e0279a45, 3d8cac1ce).
- **Plugs, moves and restarts pass with real microVMs on CI's Windows Server 2022 and 2025
  runners**: `shards plug` and `unplug` for disks and folders, `shards grow disk`, saved and
  live moves between homes with a volume's owners, modes, symlinks and device nodes kept, and
  restarts that reuse a stopped microVM's kept writable layer (D214, D190; b697d6b55).
  0.7.0's notes said `plug volume` was refused on Windows and `plug disk` untested there.
- **Hard links from Windows clients**: when you build or `cp` from a Windows machine, files
  with several names arrive as hard links, as they do from macOS and Linux, and the archive
  is byte for byte what a Unix client sends for the same tree. Docker's Windows client still
  sends each name's whole file (D180; 3c8b8eac2).
- Of the 129 build tests, 125 now build for Windows and run there, and the build context
  tests and the kept `.git` directory test run against what buildx's own file walker records
  on Windows (3b4978508, 7176e6f62, ca6100217).
- A daemon held to some of the host's CPUs gives its microVMs those alone, as on Linux
  (D125, PM M495; e2820ce9).
- How many threads a process may run is derived from what Windows charges each thread, not
  a fixed figure (D181, PM M529; cacbd8883).

### Linux

- `shards plug function` passes nested on arm64 Linux (an M5 Max) for a program that doesn't
  run as root, the device named by its PCI name or by its VFIO device node
  (`/dev/vfio/devices/vfioN`) through iommufd. The VMM's part of plugging it took 602 µs at
  the median and 626 at p90 (n 30). The first plug into a microVM took 170 ms: VFIO pins all
  of the microVM's memory for the device, faulting in what the microVM hasn't touched yet,
  and a microVM booted with a device pays the same as it starts. The whole command hasn't
  been timed yet (D214, PM M430; a45a7fca8, 72a2d1864, 0cef5fda3).

### macOS

- The CPU baseline above is built and tested on Hypervisor.framework. A guest there is shown
  less of its CPU than macOS names for the host, so a move between Macs is judged by what the
  hypervisor shows a guest, not by what macOS names (D245, PM M497, M499; 9a6f5ac59,
  abcea5f5).
- The intermittent "no grant request" stall and the CLI killed at launch were each measured
  again and not seen: none in 31,200 runs and none in 100,000 launches on an M3 Ultra
  (PM M468, M469; 784ce0777).

## Faster

- **Pooled runs.** A warm microVM makes room in its descriptor table for its run before it
  is ready. Handing a run to a warm microVM took 13.53 ms at the median and now 0.14 ms, and
  a run is usable 5.82 ms after the request at the median, down from 19.17 ms (Fedora on an
  Intel Core i9-14900HX, KVM, at load 20 to 26). Against the build before, a pooled
  `run --rm alpine true` took 15.1 ms less at the median of 150 pairs, at load 64 (D26,
  PM M470; e852e43da).
- **seccomp and device filters.** The guest kernel now compiles BPF programs. A filter's cost
  to a system call fell from 30.6 to 10.5 ns on KVM, 36.5 to 20.9 ns on Hypervisor.framework
  and 262.5 to 62.5 ns on Windows; a device filter's from 11.0 ns to nothing measurable on
  KVM, 18.2 to 2.6 ns on macOS and 200 to 25 ns on Windows. Loading a filter takes 11 to
  20 µs more, and on macOS a restored run that starts a workload holds 432 KiB more and
  starts 206 µs later (D227, PM M489; 36e475360).
- **Build policies** (`--policy`, `buildx policy eval`, `policy test`) with many rules
  compile faster: a 6,000-rule policy parsed and compiled in 299.8 ms at the median (p90
  308.6, max 313.8), down from 779.5 ms (p90 807.0, max 825.2), and a test of a deeply nested
  `every` policy took 1,736 ms at the median, down from 3,372 ms (M5 Max, n 30 and n 20,
  builds alternating; PM M414; 84ea5dbf0). `glob.match` patterns that took 1.7 s, 6.5 s and
  more than two and five minutes now take 5 to 77 ms, and numbers with millions of digits or
  huge exponents no longer run a policy out of memory (D98, PM M510, M524, M526, M537;
  825a7c6c3, d5707dbca, 944f16220, a03b37113).
- **Pushes** send as many blobs at once as pay on each path, learned as they go, where 0.7.0
  sent five, and in as few requests as the registry takes, so a registry that refuses a large
  request body can be pushed to. On one host 16 uploads at once carried 7.3 times what one
  did (D226, PM M488; 0d1fb8c2b, ef4030536). What it saves against real registries isn't
  measured yet.
- **Folders shared from Windows** no longer copy a directory's whole listing into memory each
  time a program in the microVM opens it: 100 open directories of 2,000 entries each had held
  10.77 MB (D38; d2cc3f8be).
- **`shards inspect`** with many names reads the image store once per command instead of once
  per name. How much time this saves hasn't been measured (6c9b772df).

## Changed

- **Seven binaries.** Intel Macs are unsupported, and this release has no
  `shards-darwin-amd64` (b4918cd8e).
- **The guest kernel** is `kernel-6.18.48-17c3ba205400`: it compiles BPF programs (above,
  D227; 36e475360), its virtio-mem driver lets go of an online memory block a part at a time,
  giving way to a changed request (7b807bcfb), and it runs as many vCPUs as the VMM gives it,
  255 on x86_64 and 123 on arm64 (D13; 9933b02bf; pinned in 36e5bf477).
- **Waits come from what the host shows, not from Docker's figures.** A kill waits as long as
  the microVM goes on ending, which grows with what it holds: 0.3 s for 16 GiB at the median,
  5.6 s beside a host's every CPU busy (D217, PM M480, M481, M482; c9bc0558c). A restart
  policy's waits come from what restarts cost on the host (D219, PM M484; 421fb3b65). A
  registry's waits are learned from the path to it, as TCP learns its retransmission
  timeout: of 39,260 requests to eleven registries, 25 were never answered, each a stuck
  request rather than a registry down (D222, PM M486; e7c253f16). A restart that can reuse
  a stopped microVM's kept layer goes over it or packs it, whichever its own host's restarts
  have shown quicker, learned as it runs: measured, the two crossed at 6.8 to 7.9 MiB on a
  Mac, 7.7 and 8.0 MiB on a Windows machine and 5.1 MiB on Linux (D190, PM M496;
  3afa74c62). The VMM's and the runtime's other fixed figures were audited: each is now a
  spec's, the hypervisor's, derived from what it bounds, or marked as owed a measurement
  (9bbccb203, 876922312, c38fdd13e, 453a3d4d0, 7ddceb974).
- **Every QUIC link shards makes, and the in-VM server's TLS, use AES-256-GCM alone**, both
  ways. A peer offering no AES-256-GCM is refused (D239; e12d5b96e).
- **Binds through a context are the client's folders** (above). A command that would have the
  other machine's CLI read or write that machine's files, such as `--env-file`, `cp`, a
  kernel booted directly or a build of a folder there, is refused through a context (D228;
  ea34aa231).
- **Agentfiles that can't be held are refused.** On a TCP port that one member reaches by
  name (a destination, or a remote MCP server), every other member granted that port must be
  granted the same names. An image where it isn't fails its build, naming both members, and
  remote MCP servers beside another member's other grants on one port, which built before,
  are refused alike (D236; 98921fd80).
- **`shards run container X` and `create container X`**, where `X` is a shards microVM, are
  refused and say so: `shards run vm X` runs it (D216; 9d03f9a3d).
- **A slow start is waited for.** On a slow or very busy host, a microVM still booting after a
  minute is no longer given up on: the daemon looks at each starting microVM every 10 s, and
  gives up only after a minute in which it used no more CPU than an idle one. On an emulated
  arm64 Windows host, every microVM that had been given up on was still booting. `daemon.log`
  records the CPU each starting microVM a client waits on has used (D209, PM M424;
  fcc674d6a).
- **`shards configure disk`** is refused through a context: the share of the machine's disk
  that shards keeps is the owner's to set, as `configure guest` already was (D186;
  b8270370a).

## Fixed

- **Builds held to a memory limit** (Linux). In 0.7.0 the process that writes a limited
  build's files outside its limit was refused as an unknown command, so builds wrote their
  files inside the limit and their writing steps were slower. Now the writer runs, a step's
  changes reach it a chunk at a time, writes pass through memory the build and the writer
  share, and a held build's caches are read and written outside its limit too. A build held
  to a limit short of its peak took no longer than the same build unlimited, beyond its
  rounds' spread, in all 27 host and build pairs measured (eight of CI's runners and a Fedora
  host) and on a Mac. Changes made since that run haven't been measured yet (D188, PM M442;
  9955856ee, 0c1d5901a, 0849ecb3a, 0cba57cf7, d9c42120).
- **Commands lost under load.** Of many concurrent `shards exec` commands, some could hang:
  a resumed guest could refuse an exec's connection for a busy lock, and a signal could wait
  behind a guest that reads slowly. Both are fixed, and a lost connection is now said and its
  process ended (D16, PM M541; 0d4f20288, 2944d9ab5, 3607aad11, 782275c26).
- **Contexts.** A command run with `--context default`, or under `SHARDS_CONTEXT` or
  `DOCKER_CONTEXT` naming another machine, sent shards' own helper processes to that machine,
  so the daemon never started here. Shards' own helpers now always run where they start
  (D180; f125ef3a8). Once `shards remove context` returns, nothing more reaches that machine
  through it (d91a62737, eecee5b12).
- **A build context changed while it is sent.** If a file or folder in a build's context was
  replaced by a symlink after shards listed the context and before it sent it, the build could
  send files from outside the context. Each folder is now opened inside the one above it and
  never through a link, on every platform, and on Windows unpacking onto the host (`cp` out of
  a microVM, a build's output) does the same. buildx follows such links, so here shards differs
  from Docker on purpose (5fc9b4f38, c2051c4bc).
- **PCI devices for programs that don't run as root** (Linux). A device plugged into a running
  microVM now belongs to the user the program runs as, and so does `/dev/iommu` while it is
  plugged. Before, a program run as the image's own user got "Permission denied" (D214;
  a45a7fca8, 72a2d1864).
- **A context's daemon** goes on serving after an interrupted UDP receive (c9c062278).
- **Code mode** in the in-VM server forks its workers so that they start under a seccomp
  profile that refuses `clone3`, as containers' profiles do, and survive a stop, a freeze or a
  debugger's attach on x86_64. A restore that quotes its console now keeps its working set on
  Linux and Windows (PM M525, M531; 8fce4b553, 89c6a1da9).
- **A client tells its daemon's end from its microVM's**: a run whose daemon was ended no
  longer reports that its microVM stopped before its command ended (D185, PM M530; 037fe95d4).
- **Log streams** tell a receiver that has ended the connection from one refusing a line, and
  no longer cut or stall (D163, PM M527; ca7604036, 65216745e).
- **A port chosen for TCP and UDP** is free in both (b8c98e7fe).
- **Windows:**
  - A blocking read of a Unix socket could sleep through its peer's end and wait for good,
    about once in 2,300 waits; reads now wait in `WSAPoll`, which sees it (D140, PM M536;
    7ea3ce274).
  - AWS credentials from a `credential_process` command work when the command holds JSON or
    quotes, or its program's path has spaces (e38515e59).
  - `SHARDS_CDI_SPEC_DIRS` is split at `;`, as Windows lists paths (0cbf00f3e).
  - Messages about a Dockerfile's own policy name it `Dockerfile.rego`, as buildx does on
    Windows (31b1937e1).
  - A build context's symlinks that a build follows resolve as buildx resolves them on
    Windows (e2288d4d0).
  - vCPU threads that run in short bursts keep their raised priority: Windows counts CPU time
    in 15.6 ms ticks, which had sometimes dropped such a thread to normal priority for 100 ms
    (D191; e88ff2401).
- Many intermittent test failures on CI's runners and on the emulated arm64 Windows host were
  traced to their causes and fixed (PM M466, M467, M528, M532, M533, M534, M535).

## Known limits

- **arm64 Windows**: the full test suite has not passed yet, and it has run only on an
  emulated host, where microVMs of 64 vCPUs on its 4 CPUs run very slowly (D209, PM M427). It
  has not run on arm64 Windows hardware. GPUs haven't been tested there, and a host's PCI
  device given to a microVM there is built but untested, as on x86_64 Windows.
- **Built, their runs on real microVMs owed**: members' stdio, environment, execs and
  terminals (D240, D243, D244), budgets and per-member destinations for orchestrators (D241,
  D246), GPUs by identity (D232), VM processes launched by their client (D233), the nesting
  grant (D234), Agentfile destinations (D236), carried VM and network processes (D237),
  AES-256-GCM alone (D239), the CPU baseline on KVM (D245), and projects plugged into members
  on Windows and arm64 Linux (D235). Each is unit-tested. Orchestrated image runs (D231) and
  agent control's endpoint (D238) are still being built.
- **Moves.** Between two Macs, and over Wi-Fi, moves have not been measured with a baseline.
  Live moves on arm64 Linux and arm64 Windows have not been run with real microVMs, and how
  long a live move on Windows stops its microVM has not been measured. A volume's files are
  still sent with the final pass, so large volumes lengthen the time the microVM is stopped.
- **Contexts.** Docker's CLI through a context still serves none of its client's folders, as
  its API names a path alone. A client's binds have been measured over loopback only, and a
  0.7.0 client with a 0.8.0 machine, or the other way round, hasn't been tested (D228).
- **PCI devices.** Windows' device assignment, on x86_64 and arm64, is untested on hardware
  that allows it. Linux's on x86_64 has been tested only with an emulated test device.
  Devices whose memory sits above 4 GiB can't be plugged yet. macOS offers no device
  assignment.
- **IPv6**: name lookups and published ports still reach agents over IPv4.
- **GPUs on musl** use Mesa's drivers only: NVIDIA ships no driver for musl.
