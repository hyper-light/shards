# shards 0.7.0

Windows is now a full host: microVMs from images, the daemon, snapshots, volumes and GPUs,
as on macOS and Linux. You can also plug disks, folders and PCI devices into a microVM while
it runs, grow its disks, and move it to another machine, live if you like.

Download `shards` for your machine below and check it against `SHA256SUMS`, as the
[README](../../README.md#install) shows. It is still the only file to install.

## New

### Windows runs everything

On x86_64 Windows with the Windows Hypervisor Platform turned on, shards runs what it runs on
macOS and Linux, not only kernels you boot yourself:

- `shards run vm IMAGE`, the daemon, and every microVM, image, volume and network command.
  Repeated runs of an image restore from saved copies, as on the other hosts.
- `shards save vm` and `shards restore vm`: snapshots of running microVMs.
- Volumes and binds of your own folders, with a drive's path as the source:
  `-v C:\src:/src`, `-v C:/src:/src:ro`, `--mount source=C:\src,...`. Files keep their Linux
  owners, modes, symlinks and device nodes, stored the way WSL stores them on NTFS.
- The Docker Engine API, at a named pipe only your user can open. `shards list contexts`
  shows its address in the form `DOCKER_HOST` takes (`npipe:////./pipe/...`). `docker`,
  Compose and Docker's SDKs work through it.
- Your GPU, for Vulkan in the microVM (`--gpus all`), rendered by your own driver. Tested on
  an AMD Radeon 8060S.
- `--log-driver etwlogs`: a run's output goes to Event Tracing for Windows, under the
  provider Docker uses, so the same listeners pick it up.
- `--cgroup-parent NAME`: a group of microVMs held to a memory and CPU limit together (see
  below).
- A Windows machine can serve other machines through a context (`shards run daemon --listen`).

### Plug devices into a running microVM

```console
$ shards plug disk web $PWD/data.img:/data --size 1G   # makes data.img an empty ext4 disk if it isn't there
$ shards grow disk web /data 4G                        # grows the file, the disk and its file system
$ shards unplug disk web /data
$ shards plug volume web $HOME/notes:/notes:ro         # a folder of yours, or a named volume
$ shards unplug volume web /notes
```

Every microVM made from an image now has four free PCI slots, and its saved template keeps
them, so plugging needs nothing set up ahead. What you plug is mounted at the path you name,
in the microVM's own files, and `unplug` refuses while anything there is still using it.
Files and folders are given by their absolute paths. Plugging a disk took 21 ms at p50 on an
M5 Max, and 36 ms on x86_64 Linux with KVM. This is tested on macOS and Linux; on Windows,
`plug volume` is refused for now, and `plug disk` is untested.

On Linux you can also hand the program in a microVM one of your machine's PCI devices while
it runs: start it with `--device /dev/vfio/vfio` (or `/dev/iommu`), then
`shards plug function web 0000:01:00.0`. The device must be bound to `vfio-pci`. The program
reaches it only through the microVM's IOMMU, so it can reach only the memory it maps for the
device. `shards unplug function web 0000:01:00.0` gives it back to your machine, and refuses
while anything in the microVM still has it open.

### Move a microVM to another machine

`shards move vm NAME CONTEXT` saves a running microVM here and resumes it on the machine a
context reaches, where it left off. Its image, the files it needs, its named volumes and its
log go with it. Anything the other machine already has, it doesn't send again. Its
connections are dialed again and it gets its address back on its network. If the move fails
before the microVM runs there, it keeps running here as it was.

`shards move vm --live NAME CONTEXT` copies its memory while it keeps running and stops it
only for the last pass. On a KVM host, moving a microVM between two homes stopped it for
114 ms at p50 and 140 ms at most (n 30). Before anything moves, shards checks that the
other machine's CPU has every feature this one's has, and refuses the move with the
features it lacks.

### GPUs on every Linux host

`--gpus all` now gives a microVM your Linux machine's GPU through your own Vulkan driver, as
on a Mac: NVIDIA's, AMD's and Intel's GPUs, on glibc and on musl. The static musl build
(`shards-linux-*-musl`) uses the Mesa drivers of an Alpine-style host. Tested on an Intel UHD
Graphics (Raptor Lake) and an NVIDIA RTX 4070 through Mesa's NVK.

### IPv6 for agents, on any network

An agent with IPv6 that is granted somewhere past its microVM now reaches it over IPv6 on the
default network and on networks made without `--ipv6`, including hosts that have only IPv6
addresses. Networks still deny by default: an agent reaches only the ports and servers it is
granted, over either IP version. A remote MCP server can now be written as an IPv6 address,
`http://[2001:db8::7]:8080/sse`.

### `--platform` on image commands

For an image of several platforms, `--platform` now picks one of them for
`shards remove image`, `inspect image`, `read history`, `save image`, `load image` and
`push image` (and `docker rmi`, `image inspect`, `history`, `save`, `load`, `push`).
Removing one platform frees the disk it took.

### Your own limits, on every host

`--cgroup-parent` now works everywhere:

- **Linux without systemd** (a container, or a host on OpenRC, runit or s6): name a cgroup
  delegated to you by its path, `--cgroup-parent /agents`, and its microVMs are held to the
  limits you write in `/sys/fs/cgroup/agents`.
- **macOS and Windows**: `--cgroup-parent agents` puts microVMs in a group shards keeps in
  its home, `groups/agents`, with a cgroup's files. Write a limit to its `memory.max` or
  `cpu.max` (on macOS, `memory.high` too) and its microVMs are held to it together.

### More

- `--log-driver oslog` on macOS sends a run's output to the system log, where `log show` and
  Console read it (subsystem `shards`, category the run's tag).
- `docker buildx policy eval` and `policy test` work through a context, run on the machine
  the context reaches.
- Large files in volumes (1 MiB and up) are read straight from your host's page cache, with
  no second copy in the microVM's memory. This is on by default, except in a virtual machine
  on an AMD CPU, where it would be slower.
- Snapshots, templates and warm microVMs now work on arm64 Linux too.

## Faster

- On Linux on Btrfs, a run's first write to its files no longer makes your host read 4 MiB
  around it: a repeated run of an image took 7.1 ms at p50, down from 12.0 (Fedora 44,
  Core i9-14900HX, `--cpus 1`).
- On a busy Linux host, a microVM's start no longer waits for other programs' time slices:
  with every CPU of a 4-CPU machine kept busy, a 1-CPU start's guest part took 9.2 ms at
  p50, down from 20.8 (Linux 6.12 and later).
- Restarting a stopped microVM reuses its saved writable layer where it is, rather than
  copying it, when it holds more than 5 MiB. Space its programs freed is given back to your
  disk: 1 GiB written and then deleted had kept 1 GiB on disk, and now keeps 0.56 MiB.
- Builds decompress their base image's layers once and keep them, instead of on every build.
  Where your disk can clone files (APFS, Btrfs, XFS), a built image's files are written over
  its base's, and only what the build added takes new space.
- A build held to a memory limit gives back the memory it isn't using when your machine
  runs low, and its writes to disk no longer count against that limit.

## Changed

- **Bind and volume owners.** Files your host made in a folder you bind into a microVM now
  belong to the run's user (its `--user`, else its image's `USER`), so a program that runs
  unprivileged can write to the folder it was given. A volume that an Agentfile's
  `VOLUME ... FOR` gives to one agent belongs to that agent.
- **The build cache** is no longer cleared by age. It shrinks only past the limits your disk
  settings set (`shards configure disk`), what no image uses going first, least recently
  used first, and is checked as a build grows it rather than on a timer.
- **PCI slots.** Every microVM made from an image has four empty PCI slots, for `plug`. Set
  `SHARDS_PCI_SLOTS=0` to make microVMs without them.
- **`docker history --platform`** answers that platform's history, and a platform the image
  doesn't have returns not found.
- **Saved copies.** The copies of booted microVMs that make repeated runs fast are made again
  on each image's first run after you upgrade. MicroVMs you saved with `shards save vm` on
  0.6.0 still restore.
- **Kernel.** Runs boot shards' new pinned kernel, `kernel-6.18.48-64a9427a8997`, downloaded
  on first need.

## Fixed

- A restored microVM's run now ends when you stop it, even while a command exec'd in it
  before the save is still writing.
- Stopping the daemon passes each run's end on to its client, rather than dropping it.
- Published ports are freed as soon as their microVM's network closes them.
- Many intermittent failures on busy hosts and on CI's Linux and Windows runners were traced
  to their causes and fixed.

## Known limits

- **Windows on arm64** has no hypervisor backend yet: `shards-windows-arm64.exe` runs no
  microVMs itself.
- **Live moves** are refused on arm64 Linux and on Windows, which say so. A saved move
  (without `--live`) works there. During a live move, a volume's files are sent with the
  final pass, so large volumes lengthen the time the microVM is stopped.
- **Plugging a host's PCI device** works on Linux only. It has been tested in a nested
  machine with an emulated test device, not yet on real hardware. Devices whose memory sits
  above 4 GiB can't be plugged yet. A plugged folder can't use the page-cache sharing that
  folders given at start use.
- **PCI passthrough on Windows**: the Windows hosts tested refuse device assignment, and
  shards reports their answer. macOS offers no device assignment at all.
- **IPv6**: name lookups and published ports still reach agents over IPv4.
- **GPUs on musl** use Mesa's drivers only: NVIDIA ships no driver for musl.
